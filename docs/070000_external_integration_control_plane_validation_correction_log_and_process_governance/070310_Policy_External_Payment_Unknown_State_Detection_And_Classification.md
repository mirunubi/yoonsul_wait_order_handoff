## 1. Purpose

This policy defines how yoonsul_wait_order_handoff detects, classifies, and quarantines unknown payment states created by POS, VAN, PG, simple payment, card acquirer, webhook, or settlement-channel uncertainty.

The policy prevents a payment from being treated as failed, confirmed, cancelled, refunded, or reconciled merely because a single external call timed out or returned an incomplete response.

## 2. Core Principle

An external payment state is **UNKNOWN** when the system cannot prove, with internally validated evidence, that the external financial event reached a final state.

The following rule is mandatory:

```text
Timeout is not failure.
Missing response is not failure.
Partial response is not confirmation.
Provider success text is not final authority.
Internal validation and inquiry evidence determine state authority.
```

## 3. Scope

This policy applies to all external payment-related flows including:

- POS approval and cancellation RPC responses
- VAN daemon and CAT terminal responses
- PG approval, cancel, refund, and confirm responses
- 간편결제 CPM / MPM / app-to-app flows
- Alipay / WeChatPay / cross-border payment responses
- Card acquirer / issuer approval data
- External webhook and callback events
- Settlement file corrections
- Manual provider portal checks used as emergency evidence

## 4. Unknown State Detection Triggers

A payment must be classified as UNKNOWN or one of its subtypes when any of the following conditions occur.

| Trigger | Required Classification |
|---|---|
| Request sent but no response received before timeout | `TIMEOUT_UNKNOWN` |
| Network connection closed after request transmission | `CONNECTION_LOST_UNKNOWN` |
| POS/VAN/PG response received without approval/cancel authority field | `PARTIAL_RESPONSE_UNKNOWN` |
| Response code exists but is not registered in canonical registry | `UNMAPPED_PROVIDER_CODE_UNKNOWN` |
| Response says success but approval number / transaction id is missing | `EVIDENCE_INCOMPLETE_UNKNOWN` |
| Provider webhook arrives before request response | `ASYNC_RESPONSE_PENDING_VALIDATION` |
| Late event conflicts with current internal state | `CONFLICTING_LATE_EVENT_UNKNOWN` |
| Internal order is failed but external approval evidence exists | `ORDER_PAYMENT_MISMATCH_UNKNOWN` |
| External cancel response is missing but original approval may exist | `CANCEL_RESULT_UNKNOWN` |
| Duplicate approval candidates exist for one payment intent | `DUPLICATE_APPROVAL_UNKNOWN` |
| Settlement file contains transaction not found in internal ledger | `SETTLEMENT_UNMATCHED_UNKNOWN` |
| Internal ledger contains approved payment absent from provider report | `PROVIDER_ABSENT_UNKNOWN` |

## 5. Unknown State Classification Model

Unknown states must be classified by source, risk, and recovery route.

### 5.1 Source Classification

| Source Class | Description |
|---|---|
| `REQUEST_PATH_UNKNOWN` | Unknown state generated during outbound request/response path |
| `WEBHOOK_PATH_UNKNOWN` | Unknown state generated by asynchronous callback/webhook |
| `LOCAL_DEVICE_UNKNOWN` | Unknown state generated by CAT terminal, agent daemon, serial port, or local POS failure |
| `LEDGER_MISMATCH_UNKNOWN` | Unknown state detected by internal ledger comparison |
| `SETTLEMENT_UNKNOWN` | Unknown state detected during provider settlement/deposit reconciliation |
| `MANUAL_EVIDENCE_UNKNOWN` | Unknown state created from operator/provider portal evidence pending formal validation |

### 5.2 Risk Classification

| Risk Level | Criteria | Required Handling |
|---|---|---|
| P0 | Customer may have been charged and no order exists | Immediate inquiry and manager alert |
| P1 | Order may exist without confirmed payment | Order hold and payment verification |
| P2 | Cancel/refund state uncertain | Reversal inquiry and customer notification guard |
| P3 | Settlement-only mismatch | Reconciliation exception workflow |
| P4 | Non-financial metadata mismatch | Audit queue and provider mapping review |

### 5.3 Recovery Route Classification

| Recovery Route | Used When |
|---|---|
| `PROVIDER_INQUIRY_REQUIRED` | Provider supports transaction inquiry |
| `LAST_TRANSACTION_CHECK_REQUIRED` | Terminal/POS supports last transaction lookup |
| `REVERSAL_PENDING` | Approval likely succeeded but internal order cannot be completed |
| `MANUAL_REVIEW_REQUIRED` | Automated inquiry is unavailable or inconclusive |
| `RECONCILIATION_PENDING` | Only settlement/deposit evidence can resolve the state |
| `LEGAL_EVIDENCE_HOLD` | Customer dispute, chargeback, tax, or audit risk exists |

## 6. Prohibited Handling

The system and operators must not:

1. Convert timeout directly to payment failure.
2. Ask the customer to retry payment before checking unknown-state risk.
3. Mark an order as complete without validated payment evidence.
4. Mark a cancellation/refund as complete without cancellation evidence.
5. Delete or overwrite the raw request/response payload.
6. Resolve unknown state using only a provider message string.
7. Re-run payment approval with a new idempotency key while the previous payment intent is unresolved.
8. Force ledger correction without audit reason, operator identity, and evidence attachment.

## 7. Required Evidence Before Classification Exit

An UNKNOWN state can exit quarantine only when one of the following evidence groups is attached.

| Exit Target | Required Evidence |
|---|---|
| `PAYMENT_CONFIRMED` | Approval number or provider transaction id, amount match, order match, store/terminal match, canonical response code |
| `PAYMENT_DECLINED` | Provider-decline evidence proving no financial approval occurred |
| `PAYMENT_CANCELLED` | Cancel approval number or provider cancellation transaction id |
| `PAYMENT_REFUNDED` | Refund transaction id and refund amount evidence |
| `REVERSAL_COMPLETED` | Net cancel/reversal result and original approval linkage |
| `MANUAL_SETTLED` | Manager approval, provider portal screenshot/reference, reconciliation note, audit packet |
| `RECONCILED_EXCEPTION` | Settlement file, deposit evidence, fee/tax computation, exception owner approval |

## 8. State Transition Requirements

Unknown states must move through controlled transitions only.

```text
REQUEST_SENT
→ TIMEOUT_UNKNOWN / PARTIAL_RESPONSE_UNKNOWN / RESPONSE_RECEIVED
→ INQUIRY_PENDING
→ VALIDATION_PENDING
→ CONFIRMED / DECLINED / REVERSAL_PENDING / MANUAL_REVIEW / RECONCILIATION_PENDING
→ RECONCILED / CLOSED_WITH_EXCEPTION
```

Direct transitions from `TIMEOUT_UNKNOWN` to `FAILED` are prohibited.

Direct transitions from `PARTIAL_RESPONSE_UNKNOWN` to `CONFIRMED` are prohibited.

## 9. Operator Visibility

When a payment enters UNKNOWN state, the operator console must display:

- customer-facing safe message
- internal risk level
- payment intent id
- order id
- store id
- terminal id
- provider name
- amount
- current state
- next required action
- whether customer retry is allowed
- whether goods/service handoff is allowed
- whether manager override is allowed

The customer-facing message must not imply confirmed charge, refund, or failure unless evidence exists.

## 10. Audit And Retention

Every unknown-state classification must create an audit event containing:

- detection timestamp
- source system
- trigger reason
- raw payload hash
- request id / idempotency key
- provider trace id if available
- classification code
- risk level
- assigned recovery route
- actor or automated rule id
- next review deadline

Unknown-state records must be retained according to financial evidence retention and legal hold policies.

## 11. Acceptance Criteria

This policy is implemented when:

1. All timeout and incomplete response scenarios are classified as UNKNOWN subtypes.
2. No payment can be failed or confirmed solely from a transport timeout.
3. Inquiry and validation are required before unknown-state exit.
4. Duplicate approval, late webhook, and settlement mismatch are classified separately.
5. Operator console exposes risk and next action without exposing unsafe conclusions.
6. Audit evidence exists for every unknown-state creation and closure.
