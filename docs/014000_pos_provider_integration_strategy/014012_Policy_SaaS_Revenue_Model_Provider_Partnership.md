# 014012_Policy_SaaS_Revenue_Model_Provider_Partnership

## 1. Purpose

This document defines the SaaS revenue model, payment margin opportunity, provider partnership boundary, hardware partner revenue boundary, and compliance-safe monetization policy for the Yoonsul Wait/Order Handoff project.

The previous document established the long-term strategic view:

- Yoonsul’s real competitive advantage is operation OS and Franchise OS linkage.
- Toss is the primary base provider direction.
- OKPOS compatibility is required for market coverage.
- Hardware partners should be used after software value is proven.
- SaaS monthly fee should become the main cashflow.
- Payment-related margin may become additional upside if legally and contractually available.

This document separates these revenue layers so that monetization does not compromise payment truth, provider neutrality, customer trust, audit, recovery, or compliance.

This document does not define final pricing, legal contract terms, payment commission agreements, franchise fees, or tax treatment.

It defines monetization boundaries only.

## 3. Core Principle

Revenue model must not distort runtime truth.

The project must follow this rule:

> SaaS fee, payment margin, hardware margin, setup fee, support fee, and franchise fee must be separated from payment authority, order truth, refund judgment, KDS state, customer identity, and audit evidence.

Yoonsul may monetize provider integration.

Yoonsul must not compromise operational integrity to increase transaction margin.

## 20. Provider-Neutral Monetization Rule

Yoonsul must avoid pricing that forces unsafe provider dependence.

Examples:

- do not make Toss mandatory if OKPOS store cannot migrate
- do not make OKPOS mandatory if Toss-first store is better
- do not force payment provider based only on margin
- do not lock Mini Kiosk to one payment provider
- do not lock KDS to one POS
- do not price provider gateway so that stores bypass safe integration

Provider-neutral monetization protects long-term SaaS value.

## 24. First-Store Pricing Caution

For the first store, pricing is internal.

Do not prematurely decide final SaaS price based only on first-store cost.

First store should measure:

- operational value
- support burden
- provider integration cost
- hardware reliability
- staff adoption
- customer usage
- payment recovery incidents
- KDS benefits
- setup effort

Pricing should follow evidence.

---

## 25. Store Test Partner Pricing Caution

For nearby test stores or early partners:

- use pilot pricing
- clearly label pilot scope
- avoid permanent discount promises
- preserve right to revise package
- separate hardware cost from SaaS cost
- separate provider fees from Yoonsul fees
- define support scope
- record feedback and evidence

Pilot pricing is not final SaaS pricing.

## 27. Revenue Risk Register

Revenue risks:

| Risk | Description |
| ---- | ----------- |
| Payment Margin Legal Risk | payment-related margin may require legal/provider review |
| Provider Lock-In Risk | revenue tied too heavily to one provider |
| Hardware Inventory Risk | hardware margin creates stock/support burden |
| Support Cost Risk | support workload exceeds package price |
| Franchise Pricing Risk | franchise HQ and store billing conflict |
| Discount Trap Risk | pilot discounts become expected permanent prices |
| Transaction Fee Resistance | stores resist percentage-based fees |
| Module Confusion Risk | too many add-ons confuse buyers |
| Compliance Risk | billing/payment/reporting data mishandled |
| Value Proof Risk | store does not perceive enough value for monthly fee |

Revenue risks must be tracked before scaling.

---

## 28. Mitigation

Mitigations:

- start with simple SaaS package
- keep payment margin optional
- separate provider fees from Yoonsul fees
- keep hardware partnership asset-light
- measure support cost early
- create clear module boundaries
- use pilot pricing carefully
- document value evidence
- keep provider-neutral options
- obtain legal review before payment margin
- build billing later after operational proof

---

## 29. Anti-Patterns

The following are prohibited:

- making payment margin the main reason for provider selection
- hiding provider fees inside unclear SaaS pricing
- selling hardware before software value is proven
- locking store into one provider for revenue reasons
- making refund harder because payment margin is involved
- charging for support while hiding system defects
- promising universal POS compatibility before Phase 3
- setting franchise pricing before field evidence
- mixing operational audit with billing manipulation
- overcomplicating pricing for small stores
- creating SaaS tiers that break runtime safety
