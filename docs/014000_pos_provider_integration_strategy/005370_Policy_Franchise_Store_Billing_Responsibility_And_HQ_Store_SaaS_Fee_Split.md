# 005370_Policy_Franchise_Store_Billing_Responsibility_And_HQ_Store_SaaS_Fee_Split

\#\# 1\. Purpose

This document defines the billing responsibility, HQ/store fee split, SaaS package ownership, franchise billing boundary, provider gateway cost allocation, support fee responsibility, and add-on fee governance policy for the Yoonsul Wait/Order Handoff project.

The previous document defined SaaS package tiers:

\- Store OS Basic
\- Store OS Plus
\- Store OS Pro
\- Franchise OS HQ
\- Provider Gateway Add-On
\- Mini Kiosk Add-On
\- KDS Add-On
\- Support Package
\- Analytics Add-On
\- Launch Kit

This document defines who should pay for which layer when the system expands from one store to multiple stores and later to franchise operations.

This document does not define final price amounts.

It defines billing responsibility boundaries only.

\---

\#\# 3\. Core Principle

Billing responsibility must match who receives operational value and who controls the decision.

The project must follow this rule:

\> HQ should pay for governance value, store should pay for daily operational value, and provider/payment/hardware costs should remain transparent and separable.

Do not hide HQ governance cost inside store-only fees.

Do not force store owners to pay for HQ-only control without clear value.

Do not hide provider costs inside unclear SaaS billing.

\---

\#\# 4\. Billing Layers

Yoonsul SaaS billing should be separated into layers:

| Billing Layer | Primary Beneficiary |
| \------------- | \------------------- |
| Store OS | Individual store |
| Provider Gateway | Store and HQ |
| Mini Kiosk | Store |
| KDS | Store |
| Store Support | Store |
| Franchise OS HQ | HQ / franchisor |
| HQ Analytics | HQ / multi-store owner |
| Training / SOP | HQ and store |
| Launch Kit | Store opening party |
| Hardware Bundle | Store or HQ depending on agreement |
| Payment Provider Fee | Store merchant / payment contract owner |
| Payment Margin / Referral | Separate provider contract |

Each layer should be visible.

\#\# 8\. Provider Gateway Fee Allocation

Provider Gateway fee may be allocated in several ways.

\#\#\# 8.1 Store-Paid Provider Gateway

Use when:

\- provider integration is store-specific
\- store chooses its POS/payment stack
\- store receives direct operational benefit
\- store requires OKPOS compatibility
\- store uses Mini Kiosk/KDS integration

\#\#\# 8.2 HQ-Paid Provider Gateway

Use when:

\- HQ mandates provider stack
\- HQ needs multi-store provider data
\- HQ controls vendor contract
\- HQ wants standardized integration
\- HQ absorbs technology cost

\#\#\# 8.3 Split Provider Gateway Fee

Use when:

\- HQ controls standard integration
\- store benefits from daily operation
\- provider-specific cost varies by store
\- OKPOS or local daemon creates store-specific support cost

Recommended default:

    Store pays store-specific provider gateway.
    HQ pays multi-store governance and standard provider management.

\---

\#\# 9\. Mini Kiosk Fee Allocation

Mini Kiosk fee usually belongs to the store because it directly supports store order intake.

Store benefits:

\- customer self-order
\- reduced staff order burden
\- improved order flow
\- payment surface
\- table/waiting/pickup connection
\- customer-facing multilingual UI

HQ benefits:

\- brand-consistent customer flow
\- data standardization
\- promotion control
\- menu governance

Possible allocation:

\- store pays device/module fee
\- HQ pays brand template/governance layer
\- HQ subsidizes during rollout
\- franchise launch kit includes initial setup

Recommended default:

    Store pays Mini Kiosk module.
    HQ pays brand governance layer where applicable.

\---

\#\# 10\. KDS Fee Allocation

KDS fee usually belongs to the store because it directly supports kitchen execution.

Store benefits:

\- kitchen visibility
\- ticket control
\- delay/retry/remake handling
\- order source visibility
\- reduced mistakes
\- staff workflow

HQ benefits:

\- quality consistency
\- prep-time visibility
\- store comparison
\- incident evidence

Possible allocation:

\- store pays KDS module
\- HQ pays HQ analytics/governance add-on
\- KDS included in Store OS Plus/Pro

Recommended default:

    Store pays KDS operation.
    HQ pays multi-store KDS governance.

\---

\#\# 11\. Support Package Allocation

Support package should be split by support type.

\#\#\# 11.1 Store Support

Store pays when support is for:

\- daily operations
\- device issue
\- KDS issue
\- order issue
\- staff usage
\- local provider issue
\- local recovery case

\#\#\# 11.2 HQ Support

HQ pays when support is for:

\- multi-store governance
\- franchise compliance
\- owner dispute
\- SOP change
\- menu governance
\- HQ reporting
\- brand-wide provider issue

\#\#\# 11.3 Shared Support

Split or bundled when:

\- provider outage affects multiple stores
\- franchise-wide incident occurs
\- rollout support is needed
\- store issue affects HQ compliance

Support responsibility must be written.

Analytics fee depends on use case.

HQ analytics:

\#\# 15\. Payment Provider Fee Separation

Payment provider fees should be separated from Yoonsul SaaS fee unless legally and contractually bundled.

Payment-related fees may include:

\- card transaction fee
\- PG/VAN fee
\- terminal fee
\- settlement fee
\- refund fee
\- payment provider subscription
\- payment-related referral or margin

Rules:

\- payment provider fee must be transparent
\- payment margin must not distort payment truth
\- refund decision must not depend on fee interest
\- settlement responsibility must be clear
\- payment dispute owner must be clear
\- store merchant of record must be defined

\#\# 17\. Direct Store Versus Franchise Store

\#\#\# 17.1 Direct Store

For Yoonsul-owned stores:

\- billing is internal allocation
\- measure true cost
\- track module value
\- track support burden
\- track hardware depreciation
\- track provider cost
\- use data for future pricing

\#\#\# 17.2 Franchise Store

For franchise stores:

\- billing must be contract-visible
\- fee responsibility must be clear
\- support level must be defined
\- provider fee must be disclosed
\- hardware ownership must be clear
\- data access must be governed
\- HQ/store access rights must be separated

First-store internal cost should not be confused with franchise fee.

\---

\#\# 18\. Multi-Store Operator Billing

Some customers may operate multiple stores without being formal franchise HQ.

For multi-store operators:

\- owner dashboard may be charged
\- per-store Store OS fee applies
\- multi-store analytics add-on may apply
\- provider gateway may be per store
\- support package may be operator-wide
\- role/permission structure must support multi-store access

This differs from formal franchise governance.

\#\# 20\. Billing Dispute Boundary

Billing disputes may occur when:

\- store believes HQ should pay
\- HQ believes store should pay
\- provider fee is unclear
\- hardware fee is bundled ambiguously
\- support fee is unclear
\- payment fee is confused with SaaS fee
\- module was enabled without approval
\- pilot discount expired
\- store downgraded but provider fee remains
\- device was replaced but lease continues

Required controls:

\- written fee ownership
\- module activation record
\- fee change notice
\- downgrade/cancel record
\- support tier record
\- provider fee disclosure
\- hardware ownership record

\---

\#\# 21\. Module Activation Billing Rule

A module should become billable only when:

\- module is activated
\- owner approved activation
\- scope is clear
\- support level is clear
\- provider cost is disclosed
\- hardware cost is disclosed if applicable
\- billing start date is recorded
\- cancellation/downgrade path is known

Do not bill for hidden or unclear modules.

\---

\#\# 22\. Pilot Billing Rule

Pilot billing must state:

\- pilot duration
\- pilot module scope
\- pilot price
\- standard price after pilot
\- who pays hardware
\- who pays provider fees
\- support scope
\- data use
\- conversion decision date
\- cancellation path

Pilot pricing must not become permanent by accident.

\---

\#\# 23\. Discount And Waiver Rule

Discounts and waivers must be tracked.

Fields:

\- discount id
\- customer/store/HQ
\- module
\- amount or percentage
\- reason
\- start date
\- end date
\- approver
\- renewal rule
\- impact on support
\- impact on provider fee

Discounts must not hide true support or provider cost.

\---

\#\# 24\. Package Change Rule

When package changes:

\- record old package
\- record new package
\- record effective date
\- record billing change
\- record module enable/disable
\- record data retention impact
\- record support impact
\- record provider gateway impact
\- record hardware impact
\- notify responsible party

Package change is both billing and runtime change.

\---

\#\# 25\. Data Access And Billing

Billing may affect data access.

Rules:

\- cancellation must not delete legally required records
\- downgrade may remove analytics but preserve audit
\- HQ fee cancellation may remove HQ dashboard but not store operations
\- store fee cancellation may stop new operations but preserve history as required
\- provider gateway cancellation must stop new provider events safely
\- data export rights must be defined
\- franchise relationship termination must define data ownership

Data access must not be used punitively.

\---

\#\# 26\. Anti-Patterns

The following are prohibited:

\- hiding HQ governance cost inside store-only fee
\- forcing store to pay for HQ-only analytics without value explanation
\- bundling payment provider fees without disclosure
\- hiding hardware lease inside SaaS fee without clarity
\- billing module before activation
\- continuing pilot discount without review
\- making downgrade unsafe
\- deleting evidence after cancellation
\- confusing direct-store internal cost with franchise billing
\- allowing sales discount to override provider cost
\- billing support while support ownership is unclear
\- mixing payment margin with refund decision

\#\# 29\. Conclusion

Yoonsul SaaS billing must be transparent and aligned with value.

The recommended structure is:

\- store pays for daily operational modules
\- HQ pays for franchise governance modules
\- shared modules are explicitly allocated
\- Provider Gateway may be store, HQ, or shared depending on who benefits and who controls the provider choice
\- Mini Kiosk and KDS usually belong to store-level operation
\- Franchise OS HQ belongs to HQ-level governance
\- payment provider fees must remain transparent
\- hardware cost must remain separable
\- pilot pricing must be temporary and recorded
\- package changes must be treated as runtime changes

This document prepares future SaaS and Franchise OS billing without confusing store, HQ, provider, hardware, and payment responsibilities.
