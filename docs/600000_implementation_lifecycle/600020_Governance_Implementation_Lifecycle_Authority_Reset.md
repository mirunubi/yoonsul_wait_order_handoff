### §1.3 600000 대역 전체 — NON-AUTHORITATIVE BY DEFAULT

**기존 구현 Lifecycle 산출물은 설계 근거 provenance가 재검증되기 전까지
정식 설계 근거로 사용하지 않는다.**

이는 개별 워크패킷을 무효로 판정한 것이 **아니다.**

**판정 원칙**:

> Stage 7 Approval 또는 Stage 12 Completion 기록만으로는 원천 설계 provenance가 입증되지 않는다.
> 특히 `000701` §46(근거 MD 목록 의무화)·§47(6단계 나선)·§48(증거수집 5단계 분류)의
> 현행 근거검증 절차를 거쳤다는 증거가 없는 기존 워크패킷은
> provenance가 재확인되기 전까지 권위 자료로 사용하지 않는다.

§46은 2026-07-20, §47·§48은 2026-07에 확정된 조항이다.
그 이전에 만들어진 워크패킷은 이 절차를 거칠 수 없었다.

**Human governance finding (전수 감사 결과 아님)**:

> 과거 구현 과정에서 SQL이 설계의 사실상 기준점이 되고 문서가 후행한 사례들이
> 반복되었다는 Owner 판단에 따라, 대역 전체의 기본 신뢰도를 **예방적으로** 보류한다.
> 이는 전수 조사로 확정된 사실이 아니라, 재검증 전까지의 기본값을 낮추는 결정이다.

### §1.4 증거 가치 유지

다음은 문제를 만든 자료가 아니라 **문제를 발견하거나 기록한 자료**다.

| 대상 | 취급 |
|---|---|
| 검사·감사 과정에서 획득한 **사실·재현 결과·raw evidence·defect finding** | **증거자료로 유지** |
| 의심받는 설계·워크패킷을 대상으로 내려진 **APPROVE / COMPLETE / RELEASE 판정** | **현재 권위로 승계하지 않음. 역사적 판정으로만 보존** |

구체적으로:

- `601510`(Stage 11B 블라인드 감사)이 발견한 `SECURITY DEFINER` 보안경계, SOLE 대표 유일성,
  4개념 분리 문제 → **finding은 유효**
- `601511`의 `APPROVE_WITH_NOTES` 판정 → **역사적 판정. 현재 권위 없음**
- `601400` 설계무결성 검사 프로그램의 발견 사항 → **증거자료로 유지**

`000001` §5.10에 따라 이 문서들 자체는 **수정하지 않는다.**
frozen historical snapshot은 당시에 무엇이 사실이었는지를 기록한 것이며 소급 갱신 대상이 아니다.

### §1.5 `sql/migrations/`

| 취급 | |
|---|---|
| **보존** | 현재 DB 상태에 이르는 물리적 계보 |
| **정답 아님** | 미래 설계의 기준으로 사용하지 않음 |
| **불변 여부** | 개별 migration마다 `000701` §14.5 기준으로 별도 판정 |

`000701` §14.5는 모든 migration을 무조건 불변으로 두지 않는다.
Stage 12 승인 / 보호 브랜치 포함 / 공유환경 적용 / 후속 승인 워크패킷 의존 —
이 중 하나라도 발생하면 불변으로 전환되며, 그 전까지 Draft 4조건을 모두 만족하면 수정 가능하다.
불변 경계를 넘은 migration만 forward migration(신규 번호)으로 정정한다.

`0168`/`0169`는 **동결**한다.
`601505` §4의 금지 조항(호출 금지·`ACTIVE` 승격 금지·신규 호출자 배포 금지)은 계속 유효하다.
불변 여부 판정과 물리적 처분은 새 0-A 완료 후로 유보한다.

### §2.1 착수 순서

`000701` §47.1의 6단계 나선을 그대로 따르되,
§48.4가 규정한 **1단계 직전 증거수집**을 반드시 선행한다.

```text
[1단계 직전] §48 증거수집 / provenance 조사
  - 관련 원천 설계문서 인벤토리
  - 실제 DDL / RPC / 호출자 / 로컬 DB 상태 대조
  - 문서 간 충돌·노후 항목 표시
  - §48.1 A~E 5단계 분류 및 §48.2 표 형식 필수

[1단계] Human 업무규칙 선언
  - 위 증거를 보고 무엇을 현재의 사실로 삼을지 Human이 결정
  - Human 전담, AI 위임 불가 (§47.1)

[2단계] ERD 초안
[3단계] 인접 도메인 대조 (세션 분리 필수)
[4단계] 설계문서 정합화
[5단계] SQL 구현 + 이중검증
[6단계] 나선 종료 판정
```

증거수집을 1단계 앞에 두는 이유:
검증되지 않은 옛 설계문서를 Human이 그대로 받아 적는 것을 막기 위함이다.

### §2.2 원천 설계문서도 검증된 적이 없다

`000150`/`000170`/`003020`/`009030`/`010004` 등은 **검증을 거친 적이 없다.**
확인된 노후·모순 사례:

- `000170` §14/§16의 store 서비스상태·체험상태 어휘가 구현된 적 없음 (`601601` §4.3)
- `000150` §26의 `companies`/`business_units`가 "Actual schema may be designed later" 상태로 방치
- `010004` §4는 `tenant-owned`로 한정돼 있으나 "모든 객체"로 오독되어 왔음 (`601601` §4.2)

따라서 새 0-A의 증거수집은 "검증 재개"가 아니라 **"검증 최초 수행"** 이다.

## §4 이 판정의 해제 조건

§1.3의 NON-AUTHORITATIVE 지위는 다음이 충족될 때 개별 워크패킷 단위로 해제할 수 있다.

| 검사 | 질문 |
|---|---|
| Source | 어떤 원천 설계문서를 근거로 했는가 |
| Order | 설계·검증이 SQL보다 먼저였는가 |
| Validation | 원천 설계 자체의 오류·충돌을 검사했는가 |
| Gate | 그 뒤 Stage 7 Approval을 거쳐 구현했는가 |

넷 모두 충족해야 한다. **Approval 하나만으로는 해제하지 않는다.**

다만 `Order`는 사후 판정이 어려운 항목이다.
문서에 시점 기록이 없고 §46 근거목록만으로는
"참조했다"와 "이것을 근거로 도출했다"가 구분되지 않는다.
따라서 실무상 기존 워크패킷은 **참고자료로 열람하되 근거로 인용하지 않는 것**을 원칙으로 하고,
필요한 내용은 재도출한다.
