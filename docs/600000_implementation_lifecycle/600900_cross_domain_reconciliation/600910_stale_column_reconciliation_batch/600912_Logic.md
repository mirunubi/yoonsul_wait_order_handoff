**L1142 응답 JSON 출력 키 변경 판단 근거 — 파라미터 계약(요청 방향) vs 응답 키(응답 방향) 구분(Human 요청에 따른 구분)**:

- **파라미터 계약(클라이언트 → 서버, 요청 방향)**: `place_takeout_order()`의 `p_request_memo`는 클라이언트가 호출 시 넘기는 파라미터 키다. 이건 이미 위(L508/L805)에서 `p_memo`로 변경하기로 확정됨 — 요청 방향은 원래부터 이번 Human 결정의 대상이었다.
- **응답 키(서버 → 클라이언트, 응답 방향)**: `track_takeout_order()`의 L1142 `'request_memo', v_order.request_memo`는 서버가 클라이언트에게 돌려주는 JSON 응답의 키다. 이건 파라미터 계약과 별개로, **실제로 이 키를 파싱하는 소비자가 존재하는지**가 유지/변경의 판단 기준이어야 한다.
- **이번 턴 직접 조사(저장소 전체 검색)**: `catchmenu_app/lib/**/*.dart`(실제 Flutter 클라이언트, 12개 파일) 전체에서 `request_memo`, `place_takeout_order`, `track_takeout_order` 문자열을 검색한 결과 **단 한 건도 없었다** — 즉 실제 앱은 이 RPC들을 아직 호출하지 않는다(MVP-1 Flutter 통합이 아직 시작되지 않은 상태와 일치). `sql/`, `supabase/` 전체를 검색해도 `track_takeout_order()`를 호출하거나 그 응답의 `request_memo` 키를 파싱하는 다른 SQL/edge function도 없었다. `0092`의 Dart 가이드 예시(`trackOrder()`, L397-406)조차 응답을 `Future<Map<String, dynamic>>`으로 그대로 반환할 뿐, 개별 키를 파싱하지 않는다.
- **결론**: 이 저장소 검색 범위 안에서는 `request_memo` 응답 키를 보존해야 할 API 계약상 근거를 찾지 못했다. A안(시스템 전체 용어 통일)을 그대로 적용해 L1142의 응답 키도 `memo`로 변경한다.
- **투명 공개(검증 범위의 한계)**: 이 조사는 **이 저장소 안**으로 한정됐다 — 이 저장소 밖의 별도 클라이언트 레포(있다면)는 확인하지 않았다. 그런 레포가 존재하고 이미 `request_memo` 키를 파싱하는 코드가 있다면 이 판단은 재검토가 필요하다(§5 Open Item으로 별도 기록).
- **참고 — `0099`와의 비일관성, 이번엔 손대지 않음**: `0099`의 `get_kds_realtime_state()` L448은 응답 키 `'request_memo'`를 유지하기로 이미 확정돼 있다(§2.1 위 표). 이번 A안 지시는 명시적으로 `0081`의 `track_takeout_order()`만 지정했으므로, `0099`의 출력 키는 이번 배치에서 함께 바꾸지 않는다 — 다만 "시스템 전체 용어 통일"이라는 A안의 취지와 `0099`가 남는 것 사이의 비일관성은 §5 Open Item으로 기록해 후속 결정을 요청한다.

## 3. §24 적용 방식 — 이미 여러 번 손댄 파일(`0099`) vs 첫 정정 파일(나머지 9개)

전 10개 파일 모두 `catchmenu_meta.migration_history`에 `success = true`로 이미 적용된 상태임을 재확인했다(이번 턴 쿼리 재확인) — **"아직 원본 그대로라 적용 자체가 안 된 파일"은 없다.** 대신 실질적으로 구분되는 것은 "이번이 몇 번째 §24 손질인지"다:

- **`0099` — 이미 여러 차례 §24 방식으로 손댄 파일.** `600420` 워크패킷에서 `is_late`/`priority`/`kds_capacity_threshold_per_zone`를 이미 정정·재실행했다. 이번 배치(`request_memo`, `case_severity`, `'INVESTIGATING'`)는 그 위에 **추가로 겹쳐지는 §24 정정**이다 — 소스를 고친 뒤, 체크섬을 갱신하고, **`get_kds_realtime_state()`와 `get_staff_alert_feed()` 라이브 함수 본문을 직접 재실행**해야 한다. 이전 라운드에서 고친 부분(`is_late` 등)이 이번 재실행으로 되돌아가지 않는지(같은 `CREATE OR REPLACE`가 전체 함수 본문을 교체하므로, 이번 배치의 소스 파일 자체에 이전 라운드의 수정이 이미 반영되어 있어야 함 — 아니면 퇴행) **재확인이 필수**다.
- **나머지 8개(`0081`/`0084`/`0092`/`0102`/`0104`/`0109`/`0111`/`0120`) — 이번이 첫 §24 정정.** 소스 수정 → 체크섬 갱신 → 라이브 함수 직접 재실행의 표준 §24 절차를 그대로 적용하면 된다. 단, 각 파일이 여러 함수를 정의하는 경우(`0084`는 여러 개) **영향받는 함수만** 재실행 대상으로 특정해야 한다(파일 전체를 통째로 재실행하면 그 파일의 다른, 무관한 함수까지 불필요하게 재정의하게 됨 — `CREATE OR REPLACE FUNCTION` 단위로 골라서 재실행).
- **`0133` — 표준 §24와 다른 예외 취급 필요.** 소스 수정과 체크섬 갱신은 동일하게 필요하지만, **"라이브 함수/테이블 재실행" 단계는 의미가 없다** — `0133`의 해당 블록은 `create table if not exists`이고 `0015`가 이미 실제 테이블을 만들어뒀으므로, 고친 소스를 다시 실행해도 여전히 no-op으로 스킵된다(§4). 따라서 `0133`은 "소스 정정 + 체크섬 동기화"까지만 하고, 별도의 라이브 재실행 검증 단계를 요구하지 않는다 — Stage 2 TestPlan에서 이 차이를 명시해야 한다(다른 9개와 같은 재실행 검증 절차를 `0133`에 적용하면 애초에 검증할 대상이 없다).

## 4. `0015` vs `0133`의 `reconciliation_cases` 스키마 충돌 배경

**근본 원인 정리**: `0015_create_payment_reconciliation.sql`(L10-)이 `catchmenu_payment.reconciliation_cases`를 **최초로** `create table if not exists`로 정의했다 — 컬럼명 `severity`(`default 'NORMAL'`), `case_status`(`default 'OPEN'`), 그 외 `order_id`/`ledger_id`/`intent_id`/`internal_amount`/`provider_amount`/`amount_diff`/`internal_status`/`provider_status` 등 대사(reconciliation) 특화 컬럼을 포함한 상세 스키마다.

`0133_create_final_validation_package.sql`(L273-)이 **한참 뒤에** 같은 테이블을 `case_severity`(`default 'WARNING'`)라는 다른 컬럼명과 4개짜리 축소된 상태값(`OPEN`/`INVESTIGATING`/`RESOLVED`/`WAIVED`)으로 **재정의하려 시도**했다. 그러나 `create table if not exists`는 테이블이 이미 존재하면(여기서는 `0015`가 먼저 만들어뒀으므로) **아무 것도 하지 않고 조용히 스킵**된다 — PostgreSQL의 `IF NOT EXISTS`는 "존재하면 에러를 내지 않고 넘어간다"는 뜻이지 "기존 정의를 새 정의로 갱신한다"는 뜻이 아니다.

**추정되는 경위**: `0133`은 아마 `0015`의 존재를 인지하지 못한 채(또는 `0015` 이전 시점의 오래된 설계 문서를 참고해) 이 테이블을 처음부터 다시 설계하려 한 것으로 보인다. 결과적으로 `0133`의 설계는 **한 번도 라이브에 반영되지 못한 채 무효화**됐고, 이후 작성된 여러 함수(`0084`/`0092`/`0099`/`0111`/`0120`)들이 `0133`의 (틀린) 컬럼명 가정을 따라가면서 stale 참조가 파일 여러 개로 퍼졌다 — 이게 이번 batch의 stale 값들이 반복적으로 나타나는 근본 원인으로 추정된다. `0015`가 실제 라이브 스키마의 유일한 정답 소스다.
