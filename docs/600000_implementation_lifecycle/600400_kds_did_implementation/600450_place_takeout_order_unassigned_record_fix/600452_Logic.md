## 0. 이번 재작업에서 반드시 먼저 읽어야 할 것 — 메커니즘 충돌 투명 공개

이번 지시(Human 결정 2)는 "L609/L714만 가드"하던 이전 설계의 **커버리지 진단**(L653/L852/L924/L949가 여전히 크래시한다는 Cursor+Antigravity의 발견)을 "재논의 금지"로 확정했다. **이 진단 자체는 정확하며, 전면 동의한다** — 직전 턴에 내가 자체적으로 재작성한 설계도 정확히 이 4개 경로(게스트+쿠폰없음/게스트+쿠폰ID제공/회원+쿠폰없음)의 크래시를 잡아내고, 이번 L661/L869 확장까지 포함해 11곳 전부를 재설계한다.

**단, 이번 지시가 구체적으로 명시한 수정 메커니즘("`v_customer_found and v_customer.id is not null` 형태의 boolean 가드를 9곳에 적용")은, 지시 §1이 먼저 확인하라고 요구한 바로 그 short-circuit 실증을 이번 턴에 다시 실행한 결과, 여전히 작동하지 않는 것으로 재확인됐다.** 이는 직전 턴에 이미 발견해 보고했던 사실과 정확히 동일한 결과다 — PostgreSQL 버전이나 세션 상태가 바뀐 게 아니므로 재현되는 것이 당연하지만, 지시가 명시적으로 "먼저 확인하라"고 했으므로 다시 실행했고, 결과는 바뀌지 않았다.

**해석**: "9곳 전부 가드 적용"이라는 **커버리지 요구사항**(Human 결정 2의 실질)은 그대로 수용하고 전부 반영한다. 다만 "boolean 플래그로 가드한다"는 **구체적 구현 메커니즘**은 언어 차원에서 작동하지 않음이 이번 턴에도 재확인됐으므로, 그 메커니즘 그대로 문서에 옮기면 크래시가 고쳐지지 않은 채로 "고쳐졌다"고 기록하는 결과가 된다. 이 문서는 "9곳 전부 커버"라는 실질적 요구를 스칼라 변수 치환(직전 턴에 이미 검증된, 실제로 작동하는 메커니즘)으로 달성한다. 재논의가 아니라, 지시 자체가 요구한 선행 검증 단계의 결과를 있는 그대로 보고하는 것이다.

## 1. Short-circuit 실증 — 이번 턴 재실행 (지시 §1 대응)

```sql
DO $$
declare
  v_test record;
  v_flag boolean := false;
begin
  if v_flag and v_test.id is not null then
    raise notice 'unreachable';
  end if;
  raise notice 'PASS: no crash';
end $$;
```

**결과(이번 턴 재실행)**:
```
ERROR:  record "v_test" is not assigned yet
DETAIL:  The tuple structure of a not-yet-assigned record is indeterminate.
CONTEXT:  SQL expression "v_flag and v_test.id is not null"
PL/pgSQL function inline_code_block line 6 at IF
```

`v_flag = false`인데도 크래시한다 — `v_customer_found and v_customer.id is not null` 패턴은 short-circuit되지 않는다. 원인(직전 턴에 이미 규명, 재확인만 필요): Postgres는 `v_test.id`라는 표현식을 평가하기 **전에**, 표현식을 해석(파싱/플랜 구성)하는 시점에 `v_test`의 컬럼 구조를 알아야 한다 — 무타입 `record`는 단 한 번도 `SELECT INTO`를 거치지 않으면 그 구조 자체가 없어, boolean 조건의 진위와 무관하게 해석 단계에서 실패한다. **§2에서 다시 확인하겠지만, 이 실증 결과에 따라 "전체 수정 설계 자체가 무효"라는 지시 §1의 조건문이 실제로 성립한다** — boolean 가드 메커니즘으로는 이번 재작업도 진행할 수 없다.

## 2. 채택 설계 — 스칼라 변수 치환 (boolean 가드 대신, 동일한 커버리지 목표를 실제로 달성)

`v_customer`/`v_coupon`을 무타입 `record`에서, 필요한 필드만큼의 스칼라 변수로 분해한다. 스칼라 변수는 선언 즉시 안전하게 `NULL`로 초기화되며 — `%ROWTYPE`와 마찬가지로 "구조를 모르는 상태" 자체가 존재하지 않는다 — 어떤 SQL 컨텍스트(scalar `IF`, `WHERE`절, 값 표현식)에서도 무조건 안전함을 직전 턴에 `%ROWTYPE` 실증으로 확인했다(본 문서 재작성 범위상 재실행 생략, 결과는 §0에서 인용).

```sql
declare
  ...
  -- 기존: v_customer record;
  v_customer_id uuid;
  v_customer_display_name text;
  v_customer_membership_tier text;
  v_customer_point_balance int;
  -- 기존: v_coupon record;
  v_coupon_id uuid;
  v_coupon_discount_type text;
  v_coupon_discount_value int;
  v_coupon_discount_pct int;  -- §6 Open Question 2 참고 — 컬럼 자체가 없어 항상 NULL, 별개 결함
  v_coupon_min_order_amount int;
  v_coupon_max_discount_amount int;
  ...
begin
  ...
  -- 고객 조회
  if p_customer_id is not null then
    select id, display_name, membership_tier, point_balance
    into v_customer_id, v_customer_display_name, v_customer_membership_tier, v_customer_point_balance
    from catchmenu_store.customers
    where id = p_customer_id and tenant_id = p_tenant_id and is_active = true;
  elsif p_phone_hash is not null then
    select id, display_name, membership_tier, point_balance
    into v_customer_id, v_customer_display_name, v_customer_membership_tier, v_customer_point_balance
    from catchmenu_store.customers
    where phone_hash = p_phone_hash and tenant_id = p_tenant_id and is_active = true;
  end if;
```

`v_customer_id is not null`/`v_coupon_id is not null`이 원래 코드가 `v_customer.id is not null`/`v_coupon.id is not null`로 묻고자 했던 것과 정확히 동일한 의미이며, 이제 어떤 위치에서 묻든 항상 안전하다. `v_customer_found`/`v_coupon_found` 같은 별도 플래그는 필요 없다 — `v_customer_id is not null` 자체가 곧 "식별된 고객이 있는가"를 의미한다.

## 3. Human 결정 1 반영 — 포인트 정책 A안 + 로깅 (L609)

**Human 결정(2026-07-13, 확정, 재논의 금지)**: `v_customer_id is null`인데 `p_use_points > 0`인 경우, A안(조용히 skip, 주문은 계속 진행)을 채택한다 — 핵심 기능(주문/결제)이 부가 기능(포인트) 오류로 실패해서는 안 된다는 근거. 단, 클라이언트 버그 추적을 위해 이 상황을 경고 이벤트로 기록한다.

**로깅 메커니즘 선택**: `catchmenu_ledger.events`가 아니라 `catchmenu_common.log_diagnostic()`을 사용한다. 이번 턴 확인 결과 `log_diagnostic()`은 이미 이 파일이 속한 코드베이스에서 정확히 이런 용도(예: `0028`의 `commit_kds_ticket()`이 "HOLD 티켓 없음"을 `p_log_level := 'WARNING'`으로 기록하는 데 사용)로 쓰이는 기존 진단 로그 채널이다 — `ledger.events`는 주문/결제 등 실제 비즈니스 상태 전이를 기록하는 원장이라 "클라이언트가 보낸 요청이 무시됐다"는 진단성 경고와 성격이 다르다. `log_diagnostic()`의 `p_message`는 기본값이 없는 필수 인자이므로 Stage 4 구현에서 반드시 명시해야 한다.

```sql
if v_customer_id is not null and p_use_points > 0 then
  select coalesce(
    sum(case point_type
      when 'EARN' then point_amount
      when 'USE' then -point_amount
      when 'EXPIRE' then -point_amount
      else 0
    end), 0
  )
  into v_point_balance
  from catchmenu_store.point_ledger
  where customer_id = v_customer_id
    and tenant_id = p_tenant_id;

  if v_point_balance < p_use_points then
    return catchmenu_common.build_error_response(...);
  end if;
  v_point_discount := p_use_points;
elsif v_customer_id is null and p_use_points > 0 then
  -- A안(Human 결정): 주문은 계속 진행하되 클라이언트 버그 추적용 경고 로깅
  perform catchmenu_common.log_diagnostic(
    p_tenant_id := p_tenant_id,
    p_store_id := p_store_id,
    p_log_level := 'WARNING',
    p_log_domain := 'ORDER',
    p_log_event := 'points_requested_without_customer',
    p_message := 'p_use_points > 0로 요청됐으나 식별된 고객이 없어 포인트 사용을 건너뜀',
    p_error_key := null,
    p_details := jsonb_build_object('p_use_points', p_use_points),
    p_recovery_hint := null,
    p_rpc_name := 'place_takeout_order',
    p_correlation_id := p_correlation_id,
    p_session_id := null,
    p_order_id := null,
    p_payment_id := null,
    p_exception_id := null,
    p_device_id := null,
    p_agent_id := null,
    p_caller_type := null,
    p_caller_id := null
  );
end if;
```

**주의**: 이 시점(L609 부근)은 아직 `v_order_id`/`v_session_id`가 생성되기 전이므로(주문 생성은 L790 이후) `p_order_id`/`p_session_id`는 로그에 `null`로 남긴다 — Stage 4에서 이 로그 호출을 주문 생성 이후로 옮기는 대안도 검토 가능하나, "요청 시점에 즉시 기록"이 클라이언트 버그 추적 목적에 더 부합하므로 이 위치를 기본으로 제안한다(Stage 2에서 위치 확정).

3. **쿠폰 이중 사용 레이스컨디션** — 쿠폰 유효성 확인(L642-659)과 실제 사용 처리(L852-859, `update coupon_issues set issue_status = 'USED' ... where id = p_coupon_issue_id`) 사이의 시간차 동안 같은 쿠폰이 동시 요청으로 이미 사용됐을 가능성. 현재 코드는 이 UPDATE의 영향 행 수를 확인하지 않는다. record-unassigned 문제와 완전히 별개인 동시성 결함 — 이번 workpacket 범위에서 고치지 않고 Open Item으로 이월.
