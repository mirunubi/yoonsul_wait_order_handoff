**1단계 선언과 2단계 모델을 구현 범위로 옮긴 것이며 구현 설계가 아니다.**

601803   상태 전이 모델 (Active)

## §1 Purpose

### §1.1 재작성의 원인

**`601816` §3 이 확정한 근본 원인.**

```text
계약이 허용 파일을 migration 1건으로 좁혔다
그런데 선언된 불변조건은 runtime 동작을 요구한다
```

**계약은 객체를 만들고 그 객체에 쓰거나 그것을 부르는 조작을 허용하지 않았다.**

> ⚠️ **`601816` 이 남긴 가장 정확한 표현**
>
> ```text
> 안전한 공식 경로     사용 불가   S6-3
> 위험한 기존 우회경로  사용 가능   S6-2 · S6-6
> ```
>
> **정반대로 설계됐다.**

### §1.2 재절단 — `HD-0-A-2-10`

**Human 이 2026-08-30 에 처분했다**(`601801` §3).

```text
0-A-2 는 「runtime 전체 격리」가 아니다
0-A-2 는 「안전한 격리 · 해제 전이 Kernel」이다
```

> ⚠️ **1단계 선언은 폐기되지 않았다.**
> **`HG-A-1`~`HG-A-15` 는 그대로 유지된다.**
> **4단계 산출물의 책임 범위만 다시 잘렸다.**

### §1.3 이 재절단이 세운 원칙

```text
후속 기능의 테이블을 미리 만들지 않는다
생산자와 소비자를 같은 워크패킷에서 만든다
```

**쓰는 주체 없이 저장 구조만 만든 것이 이번 실패의 형태다**(`601816` `S6-1`).
**현행 계약의 `D-2` · `D-3` 이 그 형태이며 이 문서가 그 둘을 범위에서 뺀다** — §2.3.

### §1.4 `0-A-2` 가 확정하는 것

```text
tenant_status 와 isolation_state 의 독립성을 물리적으로 성립시킨다
isolate_tenant 를 그 축에 맞게 정합화한다
격리 · 해제 · 감사 경로를 확정하고 그 경로가 실제로 성립하게 한다
```

> ⚠️ **`601802` 가 확정한 것** — `isolation_state` 를 참조하는 함수 · VIEW · MATVIEW · TRIGGER 가 **전 스키마 0개**다(§6.2).
> **`isolate_tenant` 는 `tenant_status` 에 `ISOLATED` 를 쓰며
> 그 값은 허용값 밖이라 해당 UPDATE 는 실패한다**(§5.2 · §6.1 · §9.1).
>
> **두 축 분리는 CHECK 에만 있고 로직에 없다.**
> **이 나선은 정렬이 아니라 축 신설에 가깝다**(`601803` §0.1).

**이 나선이 소유하는 상태축은 둘이다**(`HG-A-11` · `HD-0-A-2-3`).

```text
tenant_status      읽기만 한다. 변경하지 않는다
isolation_state    이 나선이 실제로 쓰기 시작한다
```

## §4 기존 함수 취급

**이 절이 이 Overview 의 핵심이다.**

### §4.1 실측

**`601802` · `601804` 가 실측한 것.**

| 함수 | 관측 |
|---|---|
| `isolate_tenant` | `tenant_status` 에 허용값 밖 값을 쓴다 — 그 경로는 실행 불가. `isolation_state` 참조 0건. `SECURITY DEFINER`. `search_path` = common,hq,ledger,audit. `EXECUTE` grantee = postgres, authenticated. DB 직접 호출자 2건 — `detect_threat` · `manage_subscription` |
| `manage_subscription` | phantom `tenants.company_name` 참조 1건. `isolate_tenant` 호출 named argument 불일치 2곳. source-state guard 없음 |
| `detect_threat` | FATAL 경로에서 `isolate_tenant` 를 호출하며 같은 named argument 불일치 |

**출처** — `601802` §5.2 · §5.3 · §9.1 · §9.2.

> ⚠️ **호출부 3곳이 모두 실제 파라미터명과 다른 이름으로 호출한다.**
> **`isolate_tenant` 는 현재 어느 호출자에서도 성립하지 않는다.**

**`601816` §0.1 이 통합자 실측으로 추가 확정한 것.**

```text
isolate_tenant     인자에 p_isolate boolean 이 있다
                   prosecdef = t · proacl = {postgres=X, authenticated=X}
authenticated      catchmenu_common USAGE = t
신규 함수 기본 ACL   PUBLIC EXECUTE
```

### §4.2 판정 — **수리한다**

**초판 판정을 유지한다. 근거 3건은 그대로다.**

```text
결론   isolate_tenant 를 같은 이름 · 같은 자리에서 정합화한다
       신규 함수를 만들고 기존을 폐기하는 재작성을 택하지 않는다
```

**근거 1 — 호출자를 고칠 수 없다**

```text
manage_subscription   HD-0-A-2-7 로 0-A-2 범위 밖
detect_threat         601505 §4 호출 금지 대상이며 0-A-2 in scope 가 아니다
```

**근거 2 — 식별자가 금지 조항의 주소다**

```text
601505 §4 호출 금지 7건이 함수명으로 지정돼 있다
600010 §1.1 이 그 금지를 0-A-2 완료까지 유효로 유지한다
```

**근거 3 — 권한 표면이 유지된다**

```text
601802 §9.2   isolate_tenant EXECUTE ACL = postgres, authenticated
```

**신규 함수는 ACL 을 새로 정해야 한다.**

> ⚠️ **근거 3 의 뜻이 §4.3 `S6-6` 판정으로 좁아졌다.**
> **「권한 표면을 건드리지 않는다」가 아니라 「식별자와 호출 지점을 보존한다」는 뜻이다.**
> **관측된 ACL 은 그대로 두어도 되는 것이 아니다** — `S6-6`.

> ⚠️ **수리의 뜻**
>
> ```text

>            보안속성과 ACL 이 확정된다 — A-9
> ```
>
> **본문 변경 방법과 물리 조작은 ChangeContract 가 정한다.**

### §4.3 Stage 6 추가 판정 — 4건

#### `S6-2` — `p_isolate` 우회를 어떻게 제거하는가

**판정 — 시그니처를 유지하고 `false` 를 무조건 거부한다.**

```text
인자를 없앤다        택하지 않는다
false 를 거부한다     택한다
```

**근거 3건**

```text
1  인자 제거는 시그니처 변경이며 CREATE OR REPLACE 로 불가하다
   DROP FUNCTION 이 필요하고 그것은 FO-12 와 충돌하며 ACL 이 소실된다
2  시그니처가 바뀌면 601505 §4 금지 조항의 주소가 바뀐다
   §4.2 근거 2 가 무너진다
3  601812 §8.2 가 이미 시그니처 불변(선택지 C)을 판정했다. 그 판정과 정합한다
```

**성립 조건** — `p_isolate` 를 거짓으로 주는 호출은 거부된다.
**해제는 `HG-A-8` 3요건을 거치는 별도 경로(`A-3` · `A-11`)로만 성립한다.**

> ⚠️ **인자는 남지만 그것으로 해제할 수 없다.**
> **`601811` 이 그 거부를 negative test 로 검사한다.**

#### `S6-4` — 신규 함수의 PUBLIC EXECUTE 를 어떻게 막는가

**판정 — `FO-7` 을 이 나선에서 부분 완화한다.**

```text
완화 대상   이 나선이 만드는 함수에 대한
            PUBLIC 회수와 소유자 지정
완화하지 않는 것
            역할에 대한 부여 — 0-C 소관 그대로
```

**근거 3건**

```text
1  HD-0-A-2-10 이 함수 보안속성 · ACL · search_path 확정을
   0-A-2 유지 항목으로 명시했다 — ACL 이 이 나선 범위에 들어왔다
2  FO-7 을 그대로 두면 신규 함수가 PUBLIC EXECUTE 로 남는다
   그 상태에서 해제 함수가 성립하면 HG-A-8 「Human 승인」이 권한으로 무너진다
3  회수는 역할 배정이 아니라 fail-closed 기본값 확정이다
   0-A 의 merchant_accounts 가 같은 형태다 — 601744 F-7
   역할에 부여하는 행위만 0-C 다 — HG-A-10 「구체적 권한 주체는 0-C 가 정한다」
```

> ⚠️ **`FO-7` 은 `601812` 소관이다.**
> **이 절은 완화의 필요와 범위를 판정한다. 조문 개정은 ChangeContract 가 한다.**

#### `S6-5` — `CREATE OR REPLACE` 시 보존할 속성을 어디에 적는가

**판정 — ChangeContract 의 함수 허용 조작에 함수별 속성표로 적는다.**

```text
적는 곳     601812 §2.5 — 각 함수의 허용 조작 행에 속성을 병기한다
적는 것     RETURNS · LANGUAGE · SECURITY DEFINER/INVOKER · 소유자 ·
            SET search_path · 기본 인자 · 반환 계약
검사하는 곳  601811 — 적용 후 카탈로그 재측정을 PASS 조건으로 삼는다
```

**근거 3건**

```text
1  CREATE OR REPLACE 는 미명시 속성을 기본값으로 되돌린다
2  601802 §9.2 가 isolate_tenant 의 현행 값을 기록했다 — 비교 기준이 존재한다
3  Overview 는 「무엇이 성립해야 하는가」만 정하고 값은 계약이 확정한다
```

#### `S6-6` — `isolate_tenant` 의 `authenticated` EXECUTE 를 어떻게 하는가

**판정 — 이 나선이 회수한다. `0-C` 로 미루지 않는다.**

**근거 4건**

```text
1  미루면 취약점이 열린 채로 남는다
   현재는 CHECK 위반으로 실행 실패라 가려져 있고 수리하면 즉시 열린다
   수리와 회수를 같은 나선에서 하지 않으면 이 나선이 취약점을 만든다
2  SECURITY DEFINER 함수가 p_tenant_id 를 인자로 받고
   authenticated 가 EXECUTE 를 가진다 — 임의 tenant 격리 · 해제가 성립한다
   601802 §9.2 · 601816 §0.1 이 실측했다
3  HG-A-10 「격리 실행 권한과 격리 해제 권한이 반드시 같지 않다」에 어긋난다
   authenticated 하나가 양쪽을 동일하게 가진다
4  회수는 역할 배정이 아니다 — S6-4 근거 3 과 같다
```

> ⚠️ **`601811` `TP-R-10` 이 「ACL 불변」을 PASS 조건으로 삼고 있다.**
> **이 판정과 충돌하므로 `601811` 이 그 기대값을 고쳐야 한다** — §6.1.

> ⚠️ **`0-C` 가 뒤이어 역할별 부여를 정한다.**
> **이 나선은 부여하지 않고 회수만 한다.**
