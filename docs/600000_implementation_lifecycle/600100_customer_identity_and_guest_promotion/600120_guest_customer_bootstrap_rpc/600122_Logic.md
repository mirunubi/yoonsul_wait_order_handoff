## 2. 헬퍼 함수 전체 DDL 초안

`customer_code` 생성은 `0058`의 `register_customer()`(L276-)가 이미 쓰는 패턴(L325 부근, `'C' || to_char(now(), 'YYMMDD') || lpad(...)`)을 그대로 재사용한다 — 새로 설계하지 않는다.

```sql
-- 0149_add_get_or_create_guest_customer_rpc.sql (번호 후보, Stage 3 재확인)
-- Depends on: 0148_add_order_sessions_customer_id_and_guest_flag.sql

create or replace function
  catchmenu_store.get_or_create_guest_customer(
  p_tenant_id uuid,
  p_phone_hash text default null
)
returns uuid
language plpgsql
volatile
security definer
set search_path = catchmenu_store
as $$
declare
  v_customer_id uuid;
  v_customer_code text;
begin
  -- customer_code 생성: 0058 register_customer()의 동일 패턴 재사용
  v_customer_code := 'C' || to_char(now(), 'YYMMDD')
    || lpad(
      (
        select coalesce(count(*), 0) + 1
        from catchmenu_store.customers
        where tenant_id = p_tenant_id
      )::text,
      6, '0'
    );

  if p_phone_hash is not null then
    -- phone_hash 있는 경우: upsert (전략 확정은 §4 참고)
    insert into catchmenu_store.customers (
      tenant_id, customer_code,
      phone_hash, is_guest,
      preferred_locale, is_active,
      first_visit_at, last_visit_at
    ) values (
      p_tenant_id, v_customer_code,
      p_phone_hash, true,
      'ko', true,
      now(), now()
    )
    on conflict (tenant_id, phone_hash)
    do update set updated_at = now()
    returning id into v_customer_id;
  else
    -- phone_hash 없는 완전 익명: 매번 신규 row (Human 결정 #4, 재논의 금지)
    insert into catchmenu_store.customers (
      tenant_id, customer_code,
      is_guest,
      preferred_locale, is_active,
      first_visit_at, last_visit_at
    ) values (
      p_tenant_id, v_customer_code,
      true,
      'ko', true,
      now(), now()
    )
    returning id into v_customer_id;
  end if;

  return v_customer_id;
end;
$$;
```

**0058 대비 필드 검토 — 이번 턴에 직접 확인, 문제 없음**: 위 DDL은 `register_customer()`가 쓰는 컬럼 목록(`store_id`, `display_name`, `phone_masked`, `acquisition_channel`, `allergen_profile`, `visit_count` 등)을 전부 채우지 않는다 — 게스트는 최소 정보만 있으면 되므로 의도적으로 줄인 것이다. 로컬 DB에서 `customers`의 `NOT NULL`이면서 기본값(default) 없는 컬럼을 직접 조회한 결과 `tenant_id`, `customer_code` 단 2개뿐이었고, 둘 다 위 DDL이 이미 채운다 — 별도 컬럼 대조 없이도 INSERT가 제약 위반 없이 성공함을 확인했다.

## 3. `0115`/`0116` 패치 — 정확한 diff

### 3.1 `0115_create_waiting_pipeline_rpc.sql` — `register_waiting()`

```diff
+  -- p_customer_id가 없으면 게스트 헬퍼로 채운다 (600120 patch)
```

`p_customer_id`가 함수 파라미터이므로 함수 본문 안에서 재대입(`p_customer_id := ...`) 가능 — 나머지 로직(대기번호 계산, Realtime 알림 등)은 전혀 건드리지 않는다. 정확히 5줄(if/call/end if + 빈 줄 1개) 삽입.

### 3.2 `0116_create_customer_app_bootstrap_rpc.sql` — `bootstrap_customer_app_v2()`

기존 L185 게이트(`if p_customer_id is not null then`) **직전**에 동일한 5줄을 삽입한다:

```diff
+  -- p_customer_id가 없으면 게스트 헬퍼로 채운다 (600120 patch)
+  if p_customer_id is null then
+    p_customer_id := catchmenu_store.get_or_create_guest_customer(
+      p_tenant_id := p_tenant_id,
+      p_phone_hash := p_phone_hash
+    );
+  end if;
+
   -- 고객 정보 + 멤버십
   if p_customer_id is not null then
     select id, display_name, membership_tier,
```

**중요**: 이 패치를 적용하면 `if p_customer_id is not null then` 게이트는 항상 참이 된다 (헬퍼가 항상 값을 채워주므로) — `600112_Logic.md` §6/`600113_TestPlan.md` §4가 지적했던 "게스트에게 caller가 customer_id를 안 넘기면 조용히 빈 결과" 위험이 **이 patch로 근본 해소된다.** `bootstrap_customer_app_v2()`는 이제 `p_phone_hash`만 있으면(또는 완전 익명이어도) 항상 게스트 데이터를 정상적으로 채워 반환한다. `600110`의 caller-contract 위험을 이 change가 실질적으로 닫는다는 점을 `600101_ChangeHistory.md`/`600102_NavigationMap.md` 갱신 시(후속 Stage) 반영할 필요가 있다.

**패치 범위 밖 확인 (이번 턴 재확인)**: `0115`의 두 번째 `customer_id` 등장 지점(L452 부근, `call_waiting_customer()` 함수)은 기존 세션을 SELECT로 읽기만 하는 곳이라 패치 불필요 — `register_waiting()`이 이미 채운 값을 그대로 읽는 것뿐이다.

## 4. ON CONFLICT 전략 확정: **DO UPDATE 채택** (DO NOTHING 기각)

지시받은 대로 재검토해 확정한다.

- **DO NOTHING 방식의 문제**: `INSERT ... ON CONFLICT (...) DO NOTHING RETURNING id`는 충돌 시 아무 행도 반환하지 않는다 — `v_customer_id`가 `null`이 되고, 별도로 `SELECT id FROM customers WHERE tenant_id=... AND phone_hash=...`를 다시 날려야 한다. 이 2단계 구조는 동시 요청 처리 시 추가 코드 경로(둘 다 필요)가 생기고, 그 경로에 버그가 생기기 쉽다.
- **DO UPDATE 방식**: `INSERT ... ON CONFLICT (tenant_id, phone_hash) DO UPDATE SET updated_at = now() RETURNING id INTO v_customer_id`는 **항상 정확히 한 행을 반환한다** — 신규 삽입이든 기존 행 충돌이든 관계없이 원자적으로 `id`를 얻는다. 동시에 같은 phone_hash로 두 요청이 들어와도 Postgres의 `INSERT ... ON CONFLICT`는 원자적이므로 두 요청 모두 **같은 customer_id**로 수렴한다 — 이것이 게스트 승격 설계(같은 row를 계속 참조)의 핵심 요구사항과 정확히 맞는다.
- `SET updated_at = now()`는 실질적으로 무해한 업데이트이나, `DO NOTHING`이 요구하는 별도 `SELECT` fallback을 없애준다는 점에서 더 단순하고 안전하다.

**결정: DO UPDATE 채택.** §2의 DDL은 이미 이 결정을 반영했다.

## 5. `security definer` 내부 `tenant_id` 검증 필요성 — Open Question

`get_or_create_guest_customer()`는 `security definer`로 RLS를 우회한다. `p_tenant_id`는 호출자가 넘기는 그대로 신뢰되며, 함수 내부에 그 값이 실제로 호출 컨텍스트(인증된 세션/스토어)와 일치하는지 검증하는 로직이 없다.

**위험 시나리오**: 만약 이 함수가 `authenticated`에게 직접 `GRANT`된다면, 악의적이거나 버그 있는 클라이언트가 임의의 `p_tenant_id`를 넘겨 다른 테넌트에 게스트 customer row를 생성할 수 있다 — cross-tenant 데이터 오염.

**Open Question**: 이 함수 내부에 `p_tenant_id`가 현재 세션의 `catchmenu_common.current_tenant_id()`(RLS 정책에서 쓰이는 것과 동일 함수로 추정, `0021`/`0081` 등에서 이미 쓰인 패턴)와 일치하는지 확인하는 방어 로직을 추가해야 하는가? 아니면 §6의 REVOKE 권장안대로 직접 노출을 막는 것으로 충분한가 — 이 둘은 상호 배타적이지 않고 심층 방어(defense in depth) 관점에서 병행 가능. 최종 확정은 Stage 2 검증 시.

## 6. 헬퍼 GRANT 범위 — Open Question, 권장안: REVOKE (간접 호출만 허용)

**권장안**: `authenticated`에게 직접 `GRANT EXECUTE`하지 않는다 (`REVOKE ALL ... FROM public`만 적용). `0115`/`0116`이 내부에서 `perform`/직접 함수 호출로만 접근하도록 한다 — 클라이언트가 `supabase.rpc('get_or_create_guest_customer', ...)`를 직접 호출할 경로 자체를 없앤다.

**근거**: 직접 노출 최소화 원칙. §5의 tenant_id 위험과 결합하면, 이 헬퍼가 직접 노출될 경우 공격 표면이 늘어난다. `0115`/`0116`은 이미 각자의 `p_tenant_id` 처리 맥락(스토어 세션, 인증된 앱 세션)을 가지고 있어 그 안에서 간접 호출되는 게 더 안전하다.

**최종 확정은 Stage 2 검증 시** — 이번 문서는 권장안만 제시, 확정 아님(지시 사항 준수).
