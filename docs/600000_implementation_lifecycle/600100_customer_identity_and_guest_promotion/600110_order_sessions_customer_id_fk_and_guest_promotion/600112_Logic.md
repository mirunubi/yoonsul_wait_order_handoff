## 1. Purpose

`600111_Overview.md`의 Candidate Affected Files를 실제 DDL/로직 수준으로 구체화한다.

## 2. DDL (실제 적용본, 0148, 커밋 `3978a14`)

`sql/migrations/0148_add_order_sessions_customer_id_and_guest_flag.sql` 실제 내용을 그대로 인용한다 (Stage 4 완료, 로컬 DB 적용 확인, 커밋 완료). 로컬 out-of-band `NO ACTION` FK를 먼저 정리(DROP)한 뒤 승인된 `SET NULL` 스펙으로 재생성하는 순서를 취한다 — 단순 `IF NOT EXISTS`만으로는 이미 존재하는 FK의 `ON DELETE` 옵션을 바꿀 수 없기 때문이다.

```sql
-- 0148_add_order_sessions_customer_id_and_guest_flag.sql
-- Depends on: 0147_widen_plan_tier_constraint.sql

alter table catchmenu_pos.order_sessions
  drop constraint if exists order_sessions_customer_id_fkey;

drop index if exists catchmenu_pos.idx_order_sessions_customer;

alter table catchmenu_pos.order_sessions
  drop column if exists customer_id;

alter table catchmenu_store.customers
  add column if not exists is_guest boolean not null default false;

alter table catchmenu_pos.order_sessions
  add column customer_id uuid
    references catchmenu_store.customers(id)
    on delete set null;

alter table catchmenu_pos.order_sessions
  add column if not exists phone_hash text;

create index idx_order_sessions_customer
  on catchmenu_pos.order_sessions(customer_id)
  where customer_id is not null;

comment on column catchmenu_store.customers.is_guest is
  'Flags a customer identity row as a guest-created identity pending in-place promotion to a member/customer account.';

comment on column catchmenu_pos.order_sessions.customer_id is
  'Optional FK linking a wait/order session to catchmenu_store.customers; ON DELETE SET NULL preserves session history when customer identity is removed.';

comment on column catchmenu_pos.order_sessions.phone_hash is
  'Hashed phone identifier used by the waiting pipeline and guest customer promotion flow; nullable for anonymous guests.';
```

`customer_id`/`phone_hash`가 먼저 `drop column if exists`로 제거된 뒤 `customer_id`는 `add column`(IF NOT EXISTS 없이, DROP 직후라 안전), `phone_hash`는 `add column if not exists`(원래 없었으므로 이 시점엔 사실상 동일 동작)로 재생성된다.

### 2.1 각 컬럼의 목적

| 컬럼 | 목적 |
|---|---|
| `customers.is_guest` | 게스트/정회원 구분 플래그. `default false`이므로 기존 실회원 row는 영향 없음. |
| `order_sessions.customer_id` | 대기/주문 세션을 고객 identity에 연결하는 FK. `0115`가 이미 이 컬럼이 있다고 가정하고 INSERT하고 있었음(§4 참고) — 이 migration이 그 가정을 현실화한다. |
| `order_sessions.phone_hash` | `0115`가 `order_sessions`에 이미 있다고 가정하고 INSERT하던 두 번째 컬럼. `0012` 원본에는 없었음 — 같은 근본 원인(설계 문서와 실제 구현 사이 문서화 안 된 격차)이므로 같은 migration에 묶는다. |

### 2.2 ON DELETE 정책

`ON DELETE SET NULL` — Human 결정 #2: 고객 삭제 시 `order_sessions` row는 보존하고 `customer_id`만 null화한다. 탈퇴 보관(retention) 메커니즘 자체는 별도 WorkPackage.

**주의**: 로컬 DB에 out-of-band로 이미 적용됐던 버전은 `ON DELETE NO ACTION`이었다 (§4 참고) — **Stage 4에서 다음과 같이 해결됨**: `0148`이 기존 FK/인덱스/컬럼을 `DROP` 후 승인된 `SET NULL` 스펙으로 재생성하는 순서를 취해, 단순 `IF NOT EXISTS` 스킵으로는 불가능했던 `ON DELETE` 옵션 교체를 실제로 완료했다. 로컬 DB 직접 조회로 `confdeltype = 'n'`(SET NULL) 확인 완료 — `600116_Verification.md` 참고.

### 2.3 인덱스

`idx_order_sessions_customer` — `customer_id is not null`인 행만 부분 인덱스로 커버. 로컬 DB의 out-of-band 적용본과 이름이 동일 (§4).

## 3. 게스트 승격(Promotion) 로직

### 3.1 Upsert 키

`customers`의 기존 `uq_customer_phone unique (tenant_id, phone_hash)` 제약(0058, 이미 존재, 재확인 완료)을 그대로 upsert 키로 사용한다 — 신규 제약 추가 불필요.

```sql
-- 게스트 주문/대기 생성 시 (예시 로직, 확정 migration 아님):
-- 1. (tenant_id, phone_hash)로 customers 조회
-- 2. 없으면 is_guest = true로 insert
-- 3. order_sessions.customer_id = 그 customers.id

-- 이후 같은 phone_hash로 회원가입 시:
update catchmenu_store.customers
set is_guest = false,
    display_name = <실제 값>,
    updated_at = now()
where id = <동일 customer_id>;
-- merge 없음, 2번째 row 없음, order_sessions.customer_id 재기입 불필요
```

### 3.2 완전 익명 게스트 (Human 결정 #4)

`phone_hash`가 전혀 없는 게스트는 dedupe 키가 없어 매 세션마다 새 `is_guest=true` row가 생성된다. 이는 승인된 제약으로 이번 범위 안에서 그대로 수용한다 (재논의 대상 아님) — 다만 `600114_ChangeContract.md`의 Open Items에 알려진 제약으로 기록한다.

## 5. Open Questions (3개, 지시된 형식 그대로)

### Open Question 1 — 005015와의 충돌

`005015_Policy_Customer_Account_Guest_Merge_Identity_Continuity_Membership_Ready_And_Runtime_Authority_Boundary.md` §5/§8/§10을 직접 재확인. §8 "Guest-To-Account Merge"는 "Before/after identity linkage," "Merge actor," "Merge timestamp" 보존을 요구 — 원래 별개인 두 identity가 merge된다는 전제다. 이번 설계(§3.1)는 애초에 같은 row를 `is_guest` 플래그만 바꾸는 in-place UPDATE라 "merge" 이벤트 자체가 없다. **충돌 있음, 재논의는 이번 범위 밖 — 005015 자체는 편집하지 않는다 (지시 사항).** Stage 2/3에서 005015에 "in-place promotion vs true merge" 구분 섹션을 추가할지 별도 결정 필요.

### Open Question 2 — 익명 게스트 dedupe 부재

§3.2 참고. Human 결정 #4로 이번 범위 안에서는 그대로 수용하지만, `is_guest=true`이고 `phone_hash`가 null인 row가 시간이 지나며 무한정 누적된다는 것 자체는 알려진 제약으로 남긴다. Device-fingerprint 기반 dedupe 키 도입 여부는 별도 결정 필요.

### Open Question 3 — 604500/600110 CHANGE_ID 중복

`docs/600000_implementation_lifecycle/604000_workpackets/604500_order_sessions_customer_id_fk_and_guest_promotion/`(잔존, `604500_Readme_...md` 1개 파일 존재)와 이번 `600100_customer_identity_and_guest_promotion/600110_.../`가 같은 CHANGE_ID(`order_sessions_customer_id_fk_and_guest_promotion`)로 중복 존재함을 이번 턴에도 재확인했다 (`find`로 두 경로 모두 실재 확인). 폴더 이동/quarantine은 지시에 따라 이번 작업에서 하지 않는다 — Open 기록만.

## 6. `0116` Caller-Contract 재확인

`bootstrap_customer_app_v2()`(0116, L185)의 `if p_customer_id is not null then` 게이트는 SQL 자체는 무손상이나, 게스트도 실제 `customer_id`를 갖게 되는 이번 설계 하에서는 **클라이언트가 게스트에게도 그 customer_id를 명시적으로 넘겨야만** 이 블록이 정상 동작한다. 넘기지 않으면 조용히 빈 결과가 나온다 — SQL 버그가 아니라 caller-contract 변경 사항이며, 이 change의 파일 범위(SQL만) 밖의 위험으로 `600114_ChangeContract.md`에도 명시한다.
