## 3. 핵심 재도출 — out-of-band NO ACTION → 정식 SET NULL 교체가 실제로 일어났음을 독립 확인

`600116_Verification.md` §3의 쿼리(`SELECT confdeltype FROM pg_constraint WHERE conname = 'order_sessions_customer_id_fkey'`)를 이번 턴에 다시 직접 실행해 재도출했다:

```
결과: n
```

`n` = SET NULL. `600112_Logic.md` §4에 기록된 out-of-band 상태(`a` = NO ACTION)에서, `0148`의 `DROP CONSTRAINT` → `ADD COLUMN` → 재생성 순서(`600115_Module.md` §1의 DDL 참고)를 통해 실제로 재조정되었음을 확인한다. 단순 `ADD COLUMN IF NOT EXISTS`만으로는 이미 존재하는 제약의 `ON DELETE` 옵션을 바꿀 수 없다는 `600114_ChangeContract.md` §4의 우려가 실제로 올바르게 해결되었다.

추가로 `600116_Verification.md` §6의 `0000` checksum 재계산(`9129ec09...`)도 `catchmenu_meta.migration_history` 기록값과의 일치를 재확인했다 — Stage 5의 독립 검증 결과를 Stage 6에서 한 번 더 재현했으며, 다른 결과가 나오지 않았다.

## 5. `applied_at` UTC 표기 관련 — 이상 아님 확인

`600116_Verification.md` §4에서 확인된 `catchmenu_meta.migration_history.applied_at = 2026-07-10 18:54:26.465814+00`(UTC)이, 실제 커밋 `3978a14`의 로컬(KST, +0900) 타임스탬프 `Sat Jul 11 03:58:30 2026 +0900`보다 날짜가 하루 앞서 보이는 현상을 검토했다.

`2026-07-10 18:54:26 UTC` + 9시간(KST 오프셋) = `2026-07-11 03:54:26 KST` — 커밋 시각(`03:58:30 KST`)보다 4분 이른 시점이다. **순서가 논리적으로 맞다**: DB에 migration을 먼저 적용(`03:54:26 KST`)한 뒤 4분 뒤 커밋(`03:58:30 KST`)한 것으로, `applied_at`이 UTC 저장 방식이라 날짜 표기만 하루 앞서 보이는 것뿐이며 실제 시간 이상은 없다.
