## Findings

1. The pull-based secondary backup correctly defaults to `--dry-run` (no destructive action without explicit `--execute`), matching the Known Constraint in `600324_ChangeContract.md` §4 that this is a PC-uptime-dependent MVP-stage backup, not an always-on cloud scheduler — no attempt was made to "fix" this by introducing always-on infrastructure.
2. The BOM discovery is a genuine, previously-latent defect: without the fix, a correctly-linked project could have been wrongly refused, which is the opposite failure direction from what the safety guard is meant to prevent (accepting a wrong project) but still a functional break (blocking all legitimate backups). This was caught and fixed before any `--execute` run occurred.
3. `cloud_target_config.py` is a pure constants module with no behavior of its own — its correctness reduces entirely to "values match `apply_migrations_cloud.py`," confirmed directly.
4. The retention/log/scheduler mechanics were independently re-verified end-to-end this turn, not accepted solely on Human's or Codex's report.

## Open Items Carried Forward

(a) **No real `--execute` cloud dump has been run yet.** All verification to date (dry-run, safety guard, retention, Task Scheduler) validates the design and safety mechanics; it does not confirm that `supabase db dump --linked` itself succeeds end-to-end against the live cloud project and produces a usable `.sql` file. The first real `--execute` run requires separate, explicit Human approval before being attempted (this is a real, irreversible-in-effect cloud read operation with real disk/time cost, not a repeat of the safe dry-run/dummy-file tests above).
