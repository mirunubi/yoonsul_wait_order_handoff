## 1. Purpose

`600321_Overview.md`의 스냅샷을 바탕으로 `tools/pull_secondary_backup.py`(신규)의 상세 설계를 기술한다. 문서만 — `.py` 파일은 이번 턴에도 생성하지 않으며, `tools/apply_migrations_cloud.py` 자체도 편집하지 않는다.

## 2. 스크립트 설계 — 단계별 흐름

### 2.1 `E:\catchmenu_backups\` 폴더 확인/생성

```python
BACKUP_DIR = Path("E:/catchmenu_backups")

def ensure_backup_dir() -> None:
    try:
        BACKUP_DIR.mkdir(parents=True, exist_ok=True)
    except OSError as e:
        # E:\ 자체가 내장 SSD라 드라이브 부재 가능성은 낮지만,
        # "당연히 있겠지"로 생략하지 않는다 — 실패 시 원인을 명확히 남기고 즉시 종료.
        log_and_exit(f"REFUSED: cannot access or create {BACKUP_DIR}: {e}")
```

`os.makedirs(exist_ok=True)`(또는 `pathlib.Path.mkdir(parents=True, exist_ok=True)`) 수준으로 처리한다. 드라이브 자체가 없거나(예: 물리적으로 분리/고장) 권한 문제로 폴더 생성이 실패하면 `OSError`가 발생하므로, 이를 잡아 **명확한 에러 메시지와 함께 즉시 종료**한다 — 조용히 넘어가거나 다른 경로로 대체하지 않는다.

### 2.2 안전장치 재구현 — 공유 설정 모듈 `tools/cloud_target_config.py` 도입 (Human 결정, 2026-07-11, Codex 검증 완료)

**정정 배경**: 이전 버전은 `EXPECTED_PROJECT_REF`를 `pull_secondary_backup.py`에 별도로 하드코딩해 `supabase/.temp/project-ref` 파일 값과 단순 문자열 대조하는 설계였다. Codex의 재현 테스트 결과, **project-ref 파일 대조만으로는 "다른 실제 프로젝트로 잘못 link된 상태"를 막지 못하는 경우가 확인됐다** — CLI가 링크 상태 자체를 그대로 신뢰하려 하는 지점이 있어, 파일 값 비교라는 사후 대조 한 겹만으로는 불충분하다. 이 발견에 따라 Human 결정으로 설계를 다음과 같이 보강한다.

**신규 파일: `tools/cloud_target_config.py`** — `apply_migrations_cloud.py`와 `pull_secondary_backup.py`가 **공유하는** 단일 설정 모듈. 이번 change(600320)의 범위에 신규 파일로 포함한다.

```python
"""Single source of truth for the approved Supabase cloud project identity.
Both tools/apply_migrations_cloud.py and tools/pull_secondary_backup.py
import from this module instead of each hardcoding their own copy of these
constants — this closes the "two independently hardcoded constants can
silently drift apart" gap recorded as an Open Question when this project
ref check was first designed.
"""

EXPECTED_PROJECT_REF = "upzthfwhtvazfftxnyfu"
EXPECTED_HOST = f"db.{EXPECTED_PROJECT_REF}.supabase.co"
EXPECTED_POOLER_USERNAME = f"postgres.{EXPECTED_PROJECT_REF}"
```

**`pull_secondary_backup.py`의 안전장치 — 이중 대조로 갱신**:

```python
from pathlib import Path
from cloud_target_config import EXPECTED_PROJECT_REF

LINKED_PROJECT_REF_FILE = Path("supabase/.temp/project-ref")

def confirm_linked_cloud_target() -> None:
    """Refuse to proceed unless the Supabase CLI's linked project matches
    the approved project ref. Reads the CLI's own linked-project cache
    file (supabase db dump --linked takes no URL argument, so there is no
    DATABASE_URL to parse the way apply_migrations_cloud.py does), then
    compares it against cloud_target_config.EXPECTED_PROJECT_REF — the
    same shared constant apply_migrations_cloud.py uses (§2.2 정정 배경
    참고 — project-ref 파일 대조 단독으로는 불충분하다는 Codex 재현
    테스트 결과에 따라, 이 상수 대조가 단일 정답 소스 역할을 한다).
    """
    if not LINKED_PROJECT_REF_FILE.exists():
        log_and_exit(
            "REFUSED: no linked Supabase project found "
            f"({LINKED_PROJECT_REF_FILE} does not exist). "
            "Run `supabase link` first. No backup was taken."
        )

    linked_ref = LINKED_PROJECT_REF_FILE.read_text(encoding="utf-8").strip()
    if linked_ref != EXPECTED_PROJECT_REF:
        log_and_exit(
            "REFUSED: linked Supabase project ref "
            f"'{linked_ref}' does not match the approved project ref "
            f"'{EXPECTED_PROJECT_REF}' (from cloud_target_config.py). "
            "No backup was taken."
        )
```

이번 턴에 `supabase/.temp/project-ref`의 실제 내용을 재확인한 결과 `upzthfwhtvazfftxnyfu`(= `EXPECTED_PROJECT_REF`)와 일치함을 확인했다 — 이 방어 코드가 정상 조건에서 통과할 대상이 실제로 존재한다.

**`apply_migrations_cloud.py`와의 관계**: 이 change(`600320`)의 Allowed Files에는 `tools/cloud_target_config.py`(신규)만 포함되며, `apply_migrations_cloud.py` 자체를 이 공유 모듈을 참조하도록 고치는 작업은 **이번 범위에 포함하지 않는다** — 이미 Audited(ACCEPT)된 파일을 다시 여는 것이므로 별도 Open Item(§5-5)으로만 기록한다.

### 2.3 클라우드 스키마 pull

```python
def run_backup() -> Path:
    timestamp = ...  # YYYYMMDD_HHMMSS 형식, Stage 4에서 datetime.now() 사용 확정
    out_path = BACKUP_DIR / f"cloud_backup_{timestamp}.sql"
    result = subprocess.run(
        ["supabase", "db", "dump", "--linked", "-f", str(out_path)],
        capture_output=True,
    )
    return out_path, result
```

`§2.2`의 `confirm_linked_cloud_target()`을 **이 호출 이전에** 반드시 실행한다.

### 2.4 보관 정책 — 최근 30일치만 유지

```python
def prune_old_backups(retention_days: int = 30) -> list[Path]:
    cutoff = datetime.now() - timedelta(days=retention_days)
    removed = []
    for f in BACKUP_DIR.glob("cloud_backup_*.sql"):
        if datetime.fromtimestamp(f.stat().st_mtime) < cutoff:
            f.unlink()
            removed.append(f)
    return removed
```

파일명의 타임스탬프가 아니라 파일 시스템의 mtime 기준으로 판단한다(둘 다 스크립트가 직접 생성하므로 사실상 동일하지만, mtime 기준이 파일명 파싱 실패에 안전하다).

### 2.5 실행 로그 — `E:\catchmenu_backups\backup_log.txt`

매 실행마다 append(덮어쓰지 않음):

```python
def append_log(success: bool, out_path: Path | None, error: str | None) -> None:
    free_bytes = shutil.disk_usage(BACKUP_DIR).free
    free_gb = free_bytes / (1024 ** 3)
    line = (
        f"{datetime.now().isoformat()} | "
        f"{'OK' if success else 'FAIL'} | "
        f"file={out_path.name if out_path else '-'} | "
        f"size_bytes={out_path.stat().st_size if (out_path and out_path.exists()) else '-'} | "
        f"free_space_gb={free_gb:.1f} | "
        f"error={error or '-'}\n"
    )
    (BACKUP_DIR / "backup_log.txt").open("a", encoding="utf-8").write(line)
```

기록 항목: 성공/실패, 파일명, 파일 크기(바이트), `E:\` 드라이브 여유 공간(GB), 에러 메시지(있으면). `shutil.disk_usage()`는 Python 표준 라이브러리로 Windows에서 그대로 동작한다.

### 2.6 실패 시 처리 — 재시도 없음

`run_backup()`(§2.3)이 실패(`returncode != 0`)하면 **재시도하지 않고** `append_log(success=False, ...)`로 로그만 남기고 프로세스를 종료한다(`sys.exit(1)`). 다음 재시도는 다음날 Task Scheduler의 정규 실행이 담당한다 — 스크립트 내부에 지수 백오프나 즉시 재시도 로직을 넣지 않는다(단순함 유지, MVP 단계 결정).

## 3. Windows Task Scheduler 등록

```powershell
schtasks /create /tn "CatchMenu_CloudSecondaryBackup" /tr "python D:\workspace\yoonsul_wait_order_handoff\tools\pull_secondary_backup.py" /sc daily /st 03:00
```

- `/sc daily /st 03:00` — 매일 1회, 새벽 3시 실행(제안 시각, §6 Open Questions에서 Human 확정 필요).
- PC가 꺼져 있으면 그 날은 실행되지 않는다(§0 Human 결정 — MVP 단계에서는 이를 감수). `schtasks`의 `/ri`(반복 간격)나 절전 해제 옵션은 이번 범위에 포함하지 않는다.
- 등록 명령 자체는 이 문서에 설계로만 기록하며, 실제 `schtasks` 실행은 Stage 4(스크립트 작성) 이후, Human 승인을 거쳐 수행한다.

## 4. `E:\` 백업과 리포 내부 `cloud_backup_*.sql`의 관계 (재확인)

이 둘은 **완전히 다른 메커니즘**이다:

| 항목 | `E:\catchmenu_backups\cloud_backup_<timestamp>.sql` (이번 change) | `cloud_backup_*.sql` (리포 루트, 오늘 이전에 `.gitignore` 처리) |
|---|---|---|
| 위치 | 리포 바깥(`E:\`, 별도 물리 디스크) | 리포 내부 루트(`D:\workspace\yoonsul_wait_order_handoff\`) |
| 생성 목적 | 정기 예약 2차 백업(재해 대비) | 일회성 조사용 덤프(오늘 세션 클라우드 감사 작업 중 생성) |
| git과의 관계 | git 추적 대상 자체가 아님(다른 드라이브) — `.gitignore` 규칙이 필요 없음 | 리포 내부라 `.gitignore`의 `cloud_backup_*.sql` 규칙으로 명시적 제외 필요했음 |
| 보관 정책 | 최근 30일 자동 순환(§2.4) | 없음(수동 관리, 1회성) |

두 메커니즘의 파일명이 `cloud_backup_` 접두사를 공유하는 것은 우연이 아니라 둘 다 `supabase db dump`(또는 유사) 계열 산출물이기 때문이지만, 자동화 여부·위치·보관 정책이 근본적으로 다르므로 혼동하지 않는다.

## 5. Open Questions

1. **보관 기간 30일의 적절성** — 스토리지 용량, 복구 시나리오상 필요 기간을 감안할 때 30일이 충분한지 Human 확정 필요.
2. **Task Scheduler 실행 시각** — 새벽 3시를 제안했으나(트래픽 최소 시간대 추정), 실제 매장 운영/야간 배치 작업과 겹치지 않는지 Human 확정 필요.
3. **복구(restore) 절차의 범위 포함 여부** — 이번 change는 백업 생성만 다룬다. 실제 장애 시 `E:\`의 덤프 파일로부터 복구하는 절차(어느 스키마/어느 시점 덤프를 언제 어떻게 적용할지)는 별도 변경건으로 분리 제안한다 — 백업이 있다고 복구 절차가 저절로 검증되는 것은 아니므로, 별도 workpacket에서 실제 복구 리허설(dry-run restore)까지 다뤄야 한다.
4. ~~`EXPECTED_PROJECT_REF` 상수의 이중 관리~~ — **해결됨(§2.2 정정)**: `tools/cloud_target_config.py` 공유 모듈 도입으로 `pull_secondary_backup.py`는 하드코딩 없이 이 모듈을 import한다.
5. **(신규) `apply_migrations_cloud.py`도 `cloud_target_config.py`를 참조하도록 리팩터할지** — 바람직하지만 이미 Audited(ACCEPT)된 파일을 다시 여는 작업이라 이번 `600320` 범위에 포함하지 않는다. 현재 `apply_migrations_cloud.py`는 자체 하드코딩 상수로 정상 동작 중이므로 시급하지 않음 — **별도 후속 변경건**으로 남긴다(이번 change에서 파일 생성/수정 없음).
