## §1 ALTER TABLE 설계

파일: 신규 마이그레이션 파일(번호 미배정 — Stage 2/4에서 배정)
테이블: `catchmenu_pos.orders`

```sql
alter table catchmenu_pos.orders
  add column requested_pickup_at timestamptz,
  add column ready_at timestamptz;
```

**사실 확인(이번 턴)**: `select count(*) from catchmenu_pos.orders;` → **0건**. 라이브 로컬 Docker DB의 `catchmenu_pos.orders`는 현재 빈 테이블이다. 이는 이번 `ALTER TABLE ... ADD COLUMN`의 안전성 판단에 참고할 사실일 뿐 — 컬럼이 nullable이고 기본값도 없으므로 행이 있었더라도 이 ALTER 자체는 즉시(테이블 전체 재작성 없이) 완료되는 종류지만, 참고로 남긴다. 판단은 별도로 필요 시 Stage 2/3에서.

**설계 근거** (`600721_Overview.md` §2 재확인 기반): 기존 `confirmed_at`/`cancelled_at`/`completed_at`(`0013` 원본 DDL)이 전부 `timestamptz`, nullable, 기본값 없음인 패턴을 그대로 따른다. `not null`을 걸지 않는 이유는 두 컬럼 모두 주문 생애주기 중 특정 시점 이전에는 자연스럽게 `NULL`이어야 하기 때문이다(주문 접수 시점엔 아직 `ready_at`이 없고, 픽업시각을 지정하지 않은 주문은 `requested_pickup_at`이 계속 `NULL`).

기본값(`default`)도 지정하지 않는다 — `ordered_at`만 `not null default now()`인 것은 "주문 생성 시각은 항상 존재해야 한다"는 의미이지, `requested_pickup_at`/`ready_at`은 애초에 선택적/이후-시점 값이므로 이 패턴이 적용되지 않는다.

## §2 영향받는 함수별 수정 후 동작 확인

컬럼 추가만으로 `.sql` 함수 본문 자체는 수정하지 않는다(이미 올바른 컬럼명을 참조하고 있었음 — 컬럼이 없었을 뿐). `600721_Overview.md` §1에서 확인한 3개 지점 각각의 예상 동작:

| 함수 | 이전 동작(컬럼 없음) | 컬럼 추가 후 예상 동작 |
|---|---|---|
| `place_takeout_order()`(`0081`) | `insert into catchmenu_pos.orders (..., requested_pickup_at, ...)`에서 `column "requested_pickup_at" of relation "orders" does not exist` 하드 에러, 트랜잭션 중단(`600616_Verification.md` §1 Test A로 실증됨) | INSERT 성공 — `p_requested_pickup_at`(nullable, 클라이언트가 안 넘기면 `NULL`)이 정상 저장됨 |
| `track_takeout_order()`(`0081`) | `select o.ready_at, o.requested_pickup_at ... into v_order`에서 동일한 "column does not exist" 하드 에러 — **이 함수는 현재 어떤 입력으로도 100% 실패**(이번 조사로 새로 확인, `600721_Overview.md` §1에 반영) | SELECT 성공 — 두 컬럼 모두 (대개 `NULL` 또는 실제 값으로) 정상 조회, 응답 JSON의 `timeline.ready_at`/`timeline.requested_pickup_at`도 정상 채워짐 |
| `call_customer_pickup()`(`0079`/`0094`, 동일 함수) | `update catchmenu_pos.orders set ..., ready_at = coalesce(ready_at, now()), ...`에서 동일한 "column does not exist" 하드 에러 — **DID 픽업 알림 후 주문 상태를 `READY`로 전환하는 기능이 현재 100% 실패** | UPDATE 성공 — `ready_at`이 최초 1회만 세팅되고(이미 값이 있으면 `coalesce`로 덮어쓰지 않음) 이후 재호출에도 안전 |

**중요 재확인**: `track_takeout_order()`와 `call_customer_pickup()` 둘 다 이번 조사 전까지 이 결함이 문서화되지 않았던 **완전히 새로운 100%-실패 발견**이다 — `600717_Audit.md`/`600404_PlaceTakeoutOrder_Defect_Roadmap.md`는 `place_takeout_order()`만 추적하고 있었고, 이 두 함수는 지금까지 어떤 Audit에도 등장한 적이 없었다. 이 컬럼 추가는 `place_takeout_order()` 하나가 아니라 **최소 3개 함수**를 동시에 고친다.

## §3 `PICKED_UP` Status Drift — Open Item으로 이월

`600721_Overview.md` §1.3에서 재확인한 대로, `call_customer_pickup()`의 `where order_status not in (..., 'PICKED_UP', ...)` 배제 조건은 `chk_order_status`에 `'PICKED_UP'`이 없어 항상 no-op이다. 이는 하드 에러가 아니고, 이번 컬럼 추가와 무관한 별개 결함이므로 이번 workpacket 범위에 포함하지 않는다. `600404_PlaceTakeoutOrder_Defect_Roadmap.md`(또는 신규 별도 트래킹)로 이월.

## Open Questions

1. **새 컬럼에 `CHECK` 제약이 필요한가?** — 현재로선 필요 없다고 판단한다. `requested_pickup_at`/`ready_at`은 임의의 과거/미래 `timestamptz` 값을 허용해야 하는 단순 타임스탬프이며(예: `ready_at >= ordered_at` 같은 논리적 제약을 걸 수도 있으나, `0013`의 기존 `confirmed_at`/`cancelled_at`/`completed_at`도 서로간 순서 제약이 전혀 없음 — 동일 패턴 유지 원칙에 따라 이번에도 제약 없이 간다). 최종 확정은 Human 결정 필요.
2. **기본값이 필요한가?** — §1에서 이미 "필요 없음"으로 판단(생애주기상 선택적/이후-시점 값이므로). 재논의 필요 시 Stage 2/3에서.
3. **`ready_at`을 세팅하는 다른 함수가 더 있는가?** — 이번 턴 `sql/migrations/*.sql` 전체를 대상으로 `ready_at` 전수 재검색을 완료했다(`600721_Overview.md` §1.1). 결과: `catchmenu_pos.orders.ready_at`을 쓰는(WRITE) 곳은 `call_customer_pickup()`(`0079`/`0094`, 동일 함수) **단 하나**이며, 읽는(READ) 곳은 `track_takeout_order()`(`0081`) **단 하나**다. 나머지 7개 파일의 `ready_at` 언급은 전부 `catchmenu_kds.kds_tickets.ready_at`(별개의, 이미 존재하는 컬럼)에 대한 것으로 재확인 완료. **범위 한계**: 이 전수 검색은 `sql/migrations/*.sql` 텍스트 검색이며, Flutter 클라이언트가 Supabase 테이블에 RLS를 통해 RPC를 거치지 않고 직접 `orders.ready_at`을 쓰는 경로가 있는지는 이번 검색 범위 밖이다(SQL 마이그레이션 검색만으로는 확인 불가) — 필요 시 별도로 Flutter RLS 정책 검토가 추가될 수 있음, 이번 문서에서는 다루지 않는다.

## Snapshot Decision

이 스냅샷으로 Stage 2 (TestPlan/ChangeContract) 진행 가능. `.sql` 파일은 이번 턴에서 수정하지 않았음.

**ChangeContract 방향 예고**: 다음 Stage 2에서 작성될 ChangeContract의 Allowed Files는 신규 마이그레이션 파일 1개(`alter table catchmenu_pos.orders add column requested_pickup_at timestamptz, add column ready_at timestamptz;`)가 될 것이다. 기존 함수 파일(`0081`/`0079`/`0094`)은 이미 올바른 컬럼명을 참조하고 있으므로 **수정 대상이 아니다** — 순수 스키마 추가만으로 3개 함수가 동시에 정상화된다.
