## Findings

1. This migration's approved scope (`requested_pickup_at`/`ready_at` columns) is fully and correctly implemented — no gaps, no drift.
2. **New defect — `order_items` stale/phantom columns, broader than a single column name.** `place_takeout_order()`'s `order_items` INSERT (`0081`) and `track_takeout_order()`'s item-list SELECT (`0081`, separate query) both reference `unit_price`/`subtotal`, neither of which exists on `catchmenu_pos.orders`. Direct reproduction surfaced `unit_price` first (Postgres reports the first invalid identifier encountered); live schema inspection shows the actual columns are `unit_price_snapshot` and `item_amount`, not simple renames-only — the INSERT additionally references `is_kds_required` (real: `is_kds_required_snapshot`) and `display_order`, which has **no corresponding column under any name** in `catchmenu_pos.order_items`'s live 28-column schema. This is wider than the single-column framing ("order_items.unit_price") this task was scoped around — full detail in Open Item (a) below.
3. **New defect — `call_customer_pickup()`'s ledger event insert uses `event_domain := 'store'`, not in `chk_event_domain`'s allowed list** (`session`/`order`/`payment`/`kds`/`delivery`/`inventory`/`staff`/`device`/`agent`/`recovery`/`knowledge`/`gateway`/`system`/`waiting` — no `'store'`). Confirmed via direct reproduction: this fires on every call to `call_customer_pickup()`, regardless of `p_queue_type`, and it fires **before** the `ready_at` UPDATE this migration fixed. Consequence: this migration's fix to `call_customer_pickup()` has not yet been exercised by any successful run — the function still fails earlier in its own body than the line this migration addressed.
4. Neither new defect is a regression from this migration — both are independently pre-existing, unrelated to the `ALTER TABLE`, surfaced only because this migration let execution advance far enough to reach them.
