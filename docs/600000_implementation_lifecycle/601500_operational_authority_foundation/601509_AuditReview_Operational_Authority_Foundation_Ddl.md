# AuditReview — 601500 Operational Authority Foundation
## Stage 11A (Claude 단독) — 2026-08-10

**판정: APPROVE\_WITH\_NOTES**

### 1. Cursor와 Claude Code 교차확인

두 검증자가 완전히 독립적으로(서로 다른 도구, 서로 다른 순서로)
검증했는데, 결과가 다음 지점에서 정확히 일치한다:
- 신규객체 개수(10컬럼+4테이블+20개 전체 테이블, 초과 0건)
- service_role 리트머스 결과(RLS가 아니라 GRANT/USAGE 계층에서
  차단)
- 멱등성(재실행 시 에러 0건)
- 기존데이터 불변(tenant1/store1)

이 정도로 세밀한 지점까지 두 독립경로가 일치한다는 건, 우연으로
보기 어렵다. 실제로 검증이 이뤄졌다는 강한 증거로 판단한다.

### 2. 금융사고 반례 시나리오 교차감사

**시나리오A**: 격리된 tenant가 여전히 과금되는가?
tenant_status=ACTIVE + isolation_state=ISOLATED가 동시에 가능
하도록 설계됨. 이게 DDL 자체의 결함은 아니지만, "격리됐는데
계속 청구된다"는 실제 비즈니스 위험이 존재한다. 다만 이건
RPC로직(0-A-2)의 문제이지, 이번 DDL의 문제는 아니다 - 스키마가
이 상태를 "표현 가능"하게 한 것과 "실제로 그런 일이 일어나게
방치"하는 건 다르다. → BLOCKING 아님, 단 0-A-2 착수 시 반드시
다뤄야 할 항목으로 명시 필요.

**시나리오B**: 같은 사업자번호로 두 개 LegalEntity를 등록할 수
있는가?
정규화된 partial unique index로 막혀있음(실증 테스트 통과:
하이픈 유무 다른 표기도 충돌 잡힘). 안전.

**시나리오C**: SOLE(단독대표) 대표자가 같은 법인에 2명 이상
존재할 수 있는가?
행단위 CHECK로는 원리적으로 못 막는다는 게 이미 문서화됨(Open
Item으로 정직하게 기록됨). 실제 법적 분쟁 소지가 있는 지점이지만,
지금 시드데이터가 0건이라 당장 위험은 없다. 다만 이 제약을
실제로 강제할 메커니즘(트리거 또는 RPC검증)이 아직 없다는 게
명확히 남아있어야 한다.

**시나리오D**: postgres 소유 전제가 깨지면 무슨 일이 일어나는가?
이미 Open Item(o)로 문서화, 에러가 아니라 "조용히 아무도 못
쓰게 되는" 최악의 실패모드라는 것까지 명시됨. 좋은 발견이었고
잘 기록됨.

**시나리오E**: ACTIVATE의 2중방벽 중 하나가 나중에 실수로 같이
제거되면?
문서에는 "행위기준 완료조건"으로 기록돼있지만, 이걸 실제로
강제하는 자동화된 장치(테스트/CI)는 없다. 사람이 문서를 안
읽고 그냥 파라미터명 오타만 고치면, 경고 없이 2중방벽이 한번에
뚫릴 수 있다. → 문서화만으로는 충분한 안전장치가 아니다.

### 3. 문서 vs 실행력의 간극

오늘 여러 차례 "행위 기준으로 완료조건을 규정한다"는 원칙이
반복 확인됐는데(예: "phantom 컬럼을 해소하는 어떤 워크패킷이든
같은 변경에서 함께 해결"), 이게 전부 산문(prose) 형태의 경고로만
남아있고 기계적으로 강제되지 않는다. 사람이 그 문서를 안 읽으면
그냥 뚫린다.

### 판정 근거

**APPROVE\_WITH\_NOTES**(BLOCK 아님, 조건부 승인)인 이유: 0168
자체의 구현은 견고하다 - 두 독립검증자가 세밀한 지점까지
일치했고, 오늘 발견된 모든 위험(tenant_status 상호파괴/RLS오류/
대표권중복/ACTIVATE조용한위반)이 실제로 설계에 반영되어 막혀
있다. 이건 BLOCK할 이유가 없다.

다만 다음 3가지를 Stage 12(Human 병합결정) 전에 명시적으로
인지하고 넘어가야 한다(구현결함 아님, 프로세스/거버넌스 공백):

1. tenant_status=ACTIVE+isolation_state=ISOLATED 동시상태의
   실제 비즈니스 의미(계속 과금할지 여부)가 아직 정책으로 정해
   지지 않음 - 0-A-2 착수 전 반드시 결정 필요
2. SOLE대표 중복방지가 문서화만 되어있고 실제 강제 메커니즘
   없음 - 향후 트리거/RPC검증 필요(지금은 시드0건이라 위험없음)
3. "행위기준 완료조건" 원칙들이 전부 산문 경고로만 존재하고
   기계적 강제(CI/테스트) 장치가 없음 - 이건 이 워크패킷만의
   문제가 아니라 프로젝트 전체의 구조적 공백

11이 종결되지 않는다.
