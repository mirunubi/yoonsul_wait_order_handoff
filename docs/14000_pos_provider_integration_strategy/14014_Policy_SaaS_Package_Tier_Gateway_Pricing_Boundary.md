# 14014_Policy_SaaS_Package_Tier_Gateway_Pricing_Boundary

## 1. Purpose

This document defines the SaaS package tier, module boundary, pricing separation, store-level billing, franchise-level billing, provider gateway add-on, Mini Kiosk/KDS add-on, support package, and future pricing governance policy for the Yoonsul Wait/Order Handoff project.

The previous document defined possible revenue layers:

- Store OS monthly fee
- Franchise OS fee
- Provider Gateway fee
- Mini Kiosk / Kiosk software fee
- KDS module fee
- support package fee
- analytics/reporting add-on
- setup/onboarding fee
- optional hardware bundle
- optional payment-related margin

This document organizes those layers into package tiers.

This document does not define final prices.

It defines package structure and pricing boundaries only.

## 3. Core Principle

Pricing must follow operational value and runtime boundary.

The project must follow this rule:

> SaaS packages should be modular enough to match store value, but not so fragmented that customers cannot understand what they are buying.

Pricing should be simple at the store level.

Architecture may be complex internally.

The customer-facing package must remain understandable.

---

## 4. Package Philosophy

Yoonsul SaaS should not be sold as only:

- POS integration
- kiosk software
- KDS screen
- payment add-on
- report dashboard

It should be sold as:

    store operation continuity and franchise-ready operating system

The package should emphasize:

- order handoff
- kitchen execution visibility
- payment recovery
- provider compatibility
- store operation dashboard
- owner/HQ visibility
- evidence/audit
- support and recovery
- future Mini Kiosk readiness

---

## 5. Recommended Package Family

Recommended package family:

| Package | Target |
| ------- | ------ |
| Store OS Basic | Single store basic operation |
| Store OS Plus | Store with KDS/recovery/provider needs |
| Store OS Pro | High-volume store or multi-device store |
| Franchise OS HQ | Franchise headquarters / multi-store owner |
| Provider Gateway Add-On | POS/payment/kiosk provider integration |
| Mini Kiosk Add-On | Customer self-order surface |
| KDS Add-On | Kitchen execution module |
| Support Package | Operational support and incident review |
| Analytics Add-On | Advanced reporting and performance insight |
| Launch Kit | Setup, onboarding, hardware partner bundle |

Final names may be changed later.

## 6. Store OS Basic

Store OS Basic may include:

- store account
- basic menu visibility
- basic order handoff dashboard
- basic order status
- basic payment status view
- basic recovery status
- basic audit log
- simple owner dashboard
- manual sold-out control
- provider-neutral runtime foundation
- limited support

Store OS Basic should not include:

- full Franchise OS
- advanced analytics
- multi-provider gateway
- Mini Kiosk software
- full KDS module
- automated provider reconciliation
- custom integration
- dedicated support

Store OS Basic is for small stores that need basic operational visibility.

---

## 7. Store OS Plus

Store OS Plus may include:

- everything in Store OS Basic
- KDS integration readiness
- provider gateway basic
- payment uncertainty handling
- cancel/refund review workflow
- staff recovery view
- support case linkage
- order source visibility
- improved owner dashboard
- basic inventory/sold-out linkage
- basic customer recovery flow
- operational evidence packet

Store OS Plus is likely the first commercially meaningful package.

It connects POS/payment/KDS/runtime recovery.

---

## 8. Store OS Pro

Store OS Pro may include:

- everything in Store OS Plus
- multiple order source support
- multiple device support
- Mini Kiosk readiness
- advanced KDS state
- advanced provider gateway
- deeper recovery workflows
- staff workflow linkage
- advanced owner dashboard
- report export with governance
- extended support
- provider incident review
- store performance report

Store OS Pro is for stores where Yoonsul becomes a key operating layer.

## 9. Franchise OS HQ

Franchise OS HQ may include:

Provider Gateway may include:

- Toss adapter
- OKPOS compatibility adapter
- PAYCO payment channel
- future Smartro/KICC/NICE/Hyphen adapters
- provider event normalization
- merchant/store mapping
- idempotency
- webhook/callback handling
- local daemon boundary
- provider evidence
- provider disable/rollback

Pricing options:

- included in Store OS Plus or Pro

- charged per store
- charged per advanced integration
- charged as setup plus monthly maintenance

Provider Gateway must remain transparent.

## 16. Hardware Bundle Boundary

Hardware bundle may include:

- tablet
- kiosk body
- payment terminal
- receipt printer
- kitchen screen
- scanner
- mounting kit
- network accessory

Rules:

- hardware bundle should not define software architecture
- hardware must be replaceable
- hardware cost must be transparent
- hardware margin must not force vendor lock-in
- certified hardware lane is required for payment terminals
- warranty/support owner must be clear

Hardware bundle should follow software runtime.

---

## 17. Payment Margin Boundary

Payment-related margin must not be packaged as hidden SaaS revenue without review.

If payment margin exists, record separately:

- provider
- contract basis
- transaction scope
- disclosure requirement
- settlement responsibility
- refund responsibility
- compliance review
- tax/accounting review
- customer impact
- store owner impact

Payment margin is optional upside.

It is not the basis for SaaS package integrity.

---

## 18. Pilot Pricing

Pilot pricing may be used for:

- first external test store
- local nearby store
- controlled partner
- early franchise candidate
- hardware partner validation

Pilot pricing rules:

- clearly marked as pilot
- limited duration
- limited scope
- no permanent discount promise
- separate hardware from SaaS
- separate provider fee from Yoonsul fee
- record feedback and evidence
- define conversion path to standard pricing

Pilot pricing is not final pricing.

---

## 19. First Store Internal Pricing

The first Yoonsul-owned store should not be used to determine final customer price directly.

First store should measure:

- actual operational value
- staff usage
- customer usage
- provider integration burden
- support burden
- KDS value
- payment recovery incidents
- Mini Kiosk value
- setup time
- hardware reliability

Pricing should follow evidence.

## 21. Package Upgrade Path

Package upgrade should be simple.

Example upgrade path:

    Store OS Basic
        -> Store OS Plus
            -> Store OS Pro
                -> Franchise OS HQ

Add-ons:

    Provider Gateway
    Mini Kiosk
    KDS
    Analytics
    Support
    Launch Kit

Upgrade should not require re-implementing provider integration from scratch.

---

## 22. Package Downgrade / Cancellation

Downgrade or cancellation must preserve operational safety.

Rules:

- disabling Mini Kiosk must not corrupt orders
- disabling Provider Gateway must stop new provider events safely
- disabling Analytics must not delete operational audit
- disabling KDS must not delete historical evidence
- canceling SaaS must preserve legally required records
- data export/deletion policy must be defined
- payment provider contract may be separate

Downgrade is a runtime event, not just billing change.

---

## 23. Package Feature Gating

Feature gating must not create unsafe partial states.

Examples:

- do not allow payment integration without recovery state
- do not allow KDS handoff without idempotency
- do not allow Mini Kiosk payment without backend verification
- do not allow analytics export without export authority
- do not allow provider gateway without audit evidence
- do not allow support console without masking

Feature gating must follow runtime safety.

---

## 24. Sales Simplicity Rule

Even if internal modules are many, customer-facing sales should be simple.

Recommended sales message:

- Basic: see and control store operations
- Plus: connect POS/KDS/payment recovery
- Pro: operate store with Mini Kiosk/KDS/provider gateway
- Franchise: manage multiple stores with governance

Avoid explaining every internal runtime detail to small store customers.

## 26. Pricing Anti-Patterns

The following are prohibited:

- too many tiny add-ons from the start
- hiding payment provider fees
- hiding hardware fees
- making support fee unclear
- forcing unsafe provider for higher margin
- charging for KDS without defining kitchen state
- charging for Mini Kiosk without recovery flow
- charging for analytics before data quality
- creating package that breaks audit or evidence
- confusing store owner with franchise HQ pricing
- making downgrade unsafe
- promising universal POS support in low tier

## 29. Conclusion

Yoonsul’s SaaS pricing should be modular but understandable.

The long-term package structure should support:

- Store OS Basic
- Store OS Plus
- Store OS Pro
- Franchise OS HQ
- Provider Gateway
- Mini Kiosk
- KDS
- Analytics
- Support
- Launch Kit
- Hardware bundle where appropriate
- Payment margin only where safe

The project must preserve the following rules:

- SaaS monthly fee is the core cashflow
- package tiers follow operational value
- provider gateway is monetizable but must remain transparent
- Mini Kiosk and KDS must not be sold without runtime safety
- hardware cost must remain separate from software value
- payment margin must be separated from payment truth
- pilot pricing is not final pricing
- franchise pricing must distinguish HQ and store value
- feature gating must not create unsafe runtime states

This document prepares future SaaS packaging without prematurely fixing final prices.
