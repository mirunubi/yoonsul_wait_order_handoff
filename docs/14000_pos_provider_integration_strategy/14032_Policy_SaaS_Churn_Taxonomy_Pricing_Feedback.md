# 14032_Policy_SaaS_Churn_Taxonomy_Pricing_Feedback

## 1. Purpose

This document defines the SaaS churn reason taxonomy, downgrade reason taxonomy, pricing resistance classification, product feedback loop, support burden feedback loop, provider issue feedback loop, module packaging correction, and Franchise OS learning policy for early SaaS customers in the Yoonsul Wait/Order Handoff project.

The previous document defined renewal, upgrade, downgrade, cancellation, exit, and reactivation governance.

This document defines how churn, downgrade, price resistance, and exit evidence must be converted into product, pricing, support, provider, and Franchise OS learning.

This document does not implement customer analytics, billing, churn prediction, pricing changes, or customer success automation.

It defines taxonomy and feedback loop policy only.

---

## 3. Core Principle

Churn is not only lost revenue.

The project must follow this rule:

> Every churn, downgrade, pricing objection, and cancellation must become structured learning that improves product scope, package design, support policy, provider strategy, and future Franchise OS readiness.

A lost customer without captured learning is a repeated future loss.

## 4. Churn Reason Taxonomy

Recommended churn reason categories:

| Churn Reason | Meaning |
| ------------ | ------- |
| VALUE_UNCLEAR | customer did not understand recurring value |
| PRICE_TOO_HIGH | price exceeded perceived value |
| STAFF_NON_ADOPTION | staff did not use the system |
| OWNER_LOW_USAGE | owner did not use dashboard or outputs |
| SUPPORT_BURDEN | support need exceeded expectation |
| PROVIDER_FAILURE | POS/payment/provider issue blocked value |
| PAYMENT_TRUST_ISSUE | payment uncertainty harmed trust |
| KDS_CONFUSION | kitchen workflow became confusing |
| MINI_KIOSK_LOW_USAGE | customer self-order value was low |
| HARDWARE_RELIABILITY | device/printer/network failures harmed use |
| DATA_MISMATCH | data did not match POS/payment reality |
| SCOPE_MISUNDERSTANDING | customer expected unsupported features |
| CONTRACT_OR_BILLING_CONFUSION | billing responsibility or contract unclear |
| STORE_OPERATION_CHANGE | store closed, moved, remodeled, changed model |
| COMPETITOR_SWITCH | customer chose another vendor |
| CUSTOM_FEATURE_GAP | customer needed specific feature not planned |
| FRANCHISE_NOT_READY | HQ/multi-store value not mature enough |
| UNKNOWN | insufficient information |

Every exit should select one primary reason and optional secondary reasons.

## 5. Downgrade Reason Taxonomy

Recommended downgrade reason categories:

| Downgrade Reason | Meaning |
| ---------------- | ------- |
| MODULE_UNUSED | module was not used enough |
| SUPPORT_TIER_TOO_HIGH | support package exceeded need |
| MINI_KIOSK_NOT_NEEDED | customer did not need customer-facing order UI |
| KDS_NOT_NEEDED | kitchen module did not fit workflow |
| ANALYTICS_NOT_NEEDED | reporting value was not perceived |
| PROVIDER_GATEWAY_OVERKILL | provider integration value was not understood |
| PRICE_REDUCTION_REQUIRED | customer needed lower monthly fee |
| STAFF_WORKFLOW_SIMPLE | store operation too simple for higher tier |
| PROVIDER_BLOCKED | provider issue made module unusable |
| HARDWARE_REMOVED | device removed or failed |
| TEMPORARY_OPERATION_CHANGE | seasonal or temporary operation reduction |
| HQ_VALUE_NOT_NEEDED | franchise/multi-store function not needed |
| UNKNOWN | insufficient information |

Downgrade is not always failure.

It may reveal correct package fit.

## 8. Churn Evidence Quality

Churn evidence quality should be classified:

- `HIGH`
- `MEDIUM`
- `LOW`
- `ANECDOTAL`
- `MISSING`
- `CONFLICTING`

Examples:

- HIGH: customer interview plus usage/support/provider records
- MEDIUM: customer explanation plus partial usage data
- LOW: informal reason only
- ANECDOTAL: secondhand or short comment
- MISSING: customer left without reason
- CONFLICTING: owner and usage data disagree

Do not overreact to low-quality churn evidence.

## 9. Product Feedback Loop

Churn must feed product decisions.

Product feedback outputs:

- improve existing module
- simplify module
- split module
- merge module
- remove module from early package
- defer module
- create training material
- create support guide
- add test case
- create blocker
- create new document
- update onboarding
- update dashboard
- update Mini Kiosk flow
- update KDS flow
- update payment recovery flow

Product feedback should be recorded as controlled input, not immediate build command.

## 10. Pricing Feedback Loop

Pricing feedback outputs:

- revise package explanation
- revise package boundary
- revise module bundle
- create lower entry tier
- create support add-on
- separate hardware fee
- separate provider fee
- revise pilot discount rule
- revise early adopter discount
- revise store/HQ split
- defer transaction-based pricing
- simplify quote format
- create value proof material

Pricing feedback should not automatically reduce price.

Sometimes the right answer is better value explanation, not discount.

## 19. Franchise OS Feedback Loop

Franchise-related feedback should update:

- HQ dashboard roadmap
- multi-store comparison
- billing responsibility
- store/HQ access boundary
- SOP/training linkage
- menu governance
- provider standardization
- support escalation
- franchise technology fee hypothesis
- rollout timing

Franchise OS should not be accelerated just because one owner asks.

Franchise OS readiness requires stable store-level runtime.

---

## 20. Churn Pattern Review

Churn should be reviewed in patterns.

Review after:

- first 3 exits
- first 5 downgrades
- first 10 pricing objections
- repeated provider-related churn
- repeated staff non-adoption
- repeated Mini Kiosk abandonment
- repeated KDS confusion
- repeated support overload
- repeated payment trust issue

One churn can be anecdotal.

Repeated churn is signal.

---

## 21. Churn Severity

Recommended churn severity values:

- `CRITICAL`
- `HIGH`
- `MEDIUM`
- `LOW`
- `INFO`

Severity examples:

- CRITICAL: payment trust issue caused exit
- HIGH: provider failure caused exit
- HIGH: staff non-adoption repeats across stores
- MEDIUM: price objection without product failure
- LOW: store closed for unrelated reason
- INFO: downgrade due to correct package fit

Severity should affect roadmap review.

## 25. Discount Feedback Rule

Discounts should be analyzed.

When discount is used, record:

- reason for discount
- customer value perception before discount
- whether discount solved churn risk
- whether discount only delayed churn
- module usage after discount
- support burden after discount
- renewal result
- standard price conversion possibility

Discount is not proof of product value.

---

## 26. Package Correction Rule

Package should be corrected when churn patterns show:

- package too broad
- package too narrow
- module bundled too early
- provider fee confused with SaaS fee
- support tier mismatched
- Mini Kiosk value unclear
- KDS value underexplained
- analytics introduced too early
- Franchise OS promise premature
- hardware cost hidden

Package correction should be documented.

---

## 27. Sales Message Correction Rule

Sales message should be corrected when customers misunderstand:

- what is included
- what is not included
- provider limitations
- support scope
- hardware responsibility
- payment margin or fee
- Mini Kiosk readiness
- KDS readiness
- Franchise OS maturity
- universal POS compatibility

Misunderstanding-driven churn is preventable.

---

## 28. Provider Position Correction Rule

Provider position should be corrected when churn shows:

- provider is too unreliable
- provider support is weak
- provider data access is insufficient
- provider cost is too high
- provider blocks Mini Kiosk
- provider creates KDS ambiguity
- provider refund/cancel flow is unclear
- provider causes customer trust issue
- provider requires too much support

Provider status may change from active candidate to deferred or blocked.

---

## 29. Reactivation Learning

Former customers may reactivate if:

- previous blocker resolved
- pricing package changed
- support model improved
- provider issue fixed
- hardware reliability improved
- module simplified
- Franchise OS became relevant
- store operation changed

Reactivation outreach should be based on known exit reason.

Do not re-approach without solving the reason they left.

---

## 30. Anti-Patterns

The following are prohibited:

- treating churn as personal failure and hiding it
- recording churn only as price issue without evidence
- reducing price before understanding value gap
- blaming staff without reviewing workflow
- blaming provider without evidence
- ignoring payment trust churn
- ignoring hardware reliability churn
- ignoring owner low usage
- ignoring support burden
- building custom feature for one churn without pattern
- changing package based on one anecdote
- ignoring repeated churn patterns
- using discount to hide product weakness
- deleting churn evidence

## 33. Conclusion

Churn, downgrade, pricing resistance, and exit are not just losses.

They are structured inputs for improving:

- product scope
- package design
- pricing message
- support tier
- provider strategy
- Mini Kiosk
- KDS
- payment recovery
- hardware bundle
- staff adoption
- owner dashboard
- Franchise OS timing

The correct feedback loop is:

    Churn / Downgrade / Pricing Objection
        -> Reason Taxonomy
        -> Evidence Quality
        -> Severity
        -> Feedback Loop Record
        -> Product / Pricing / Support / Provider / Franchise OS Action
        -> Next Review

This document ensures that early SaaS losses become disciplined learning instead of repeated mistakes.
