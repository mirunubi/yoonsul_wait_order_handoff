# 024160_Policy_First_30_Days_Troubleshooting_And_Conversion_Readiness

Legacy path: $old.

1\. Purpose

This document defines the First 30 Days Troubleshooting and Conversion Readiness policy for CatchMenu / Wait Order Handoff.

The first 7 days confirm activation.

The first 30 days confirm whether CatchMenu becomes part of real store operation.

During the first 30 days, CatchMenu must detect operational friction, stabilize menu accuracy, confirm request board adoption, evaluate manual POS fallback burden, identify POS/KDS integration need, collect merchant feedback, resolve support issues, and prepare evidence for paid conversion.

Core purpose:

Define first 30 days troubleshooting.
Confirm real operational usage.
Check menu stabilization.
Check request board adoption.
Check staff workload.
Check manual POS fallback burden.
Identify POS integration readiness.
Identify KDS integration readiness.
Collect usage evidence.
Collect merchant feedback.
Resolve support cases.
Evaluate conversion readiness.
Prevent trial failure caused by unresolved early friction.

3\. Core Principle

The first 30 days prove operating habit and conversion readiness.

Core rule:

First 7 days proves activation.
First 30 days proves operating habit and conversion readiness.

Korean rule:

초기 7일은 작동 여부를 증명한다.

5\. Review Timeline

Suggested first 30 days timeline:

Day 1-7:
activation check and blocker resolution

Day 8-14:
usage and staff adoption check

Day 15:
midpoint merchant feedback review

Day 16-23:
troubleshooting and menu/request stabilization

Day 24-27:
conversion readiness and blocker review

Day 28-30:
conversion discussion or recovery preparation

Core rule:

Do not wait until trial end to discover first-month friction.

TROUBLESHOOTING\_REQUIRED

CONVERSION\_READY

Usage evidence should be reviewed during first 30 days.

Metrics may include:

Entry Plate scan count
menu view count
language selection count
item detail view count
request send count
request confirmation count
unconfirmed request count
repeat guest/session count
Owner Console login count

support case count

Core rule:

Conversion discussion should use evidence, not only impression.

8\. Low Usage Detection

Low usage may indicate bad placement, staff resistance, poor guest awareness, or weak value fit.

Low usage signals:

few or no scans
menu views without requests
requests sent but not confirmed
Owner Console rarely opened
staff does not mention service
merchant forgot trial is active
Entry Plate placed in low-visibility area

Possible responses:

recheck Entry Plate placement
explain service again
train staff
improve guest-facing notice
simplify menu/request flow
check merchant fit
schedule follow-up

Core rule:

Low usage is a signal to troubleshoot before judging product value.

9\. Menu Stabilization Review

First 30 days should confirm that the menu is trusted.

Review items:

wrong item reports
wrong price reports
missing item reports
wrong option reports
translation concerns
critical warning concerns
category confusion
sold-out handling
menu update frequency
merchant confidence in menu

Core rule:

If the merchant does not trust the menu, the merchant will not trust the service.

10\. Request Board Adoption Review

Request board adoption should be verified.

Review items:

request board opened during service
responsible staff identified
requests confirmed or handled
unconfirmed requests reviewed
staff understands status meanings
owner knows warning rules
request board location visible
tablet/PC/mobile access usable

Core rule:

Request board adoption is a habit, not a one-time explanation.

11\. Staff Workload Review

Staff workload should be reviewed honestly.

Positive signs:

less repeated menu explanation
foreign guest communication easier
request content clearer
staff can process request quickly
owner sees reduced friction

Negative signs:

staff checks too many screens
manual POS entry too slow
requests are duplicated
staff ignores request board
staff feels service adds work

Core rule:

Merchant Success must reduce friction, not hide it.

12\. Manual POS Fallback Burden Review

Before full POS integration, manual POS fallback may be acceptable.

Review items:

how often manual POS entry occurs
how long manual entry takes
whether duplicate entry occurs
whether staff understands request summary
whether options are clear
whether payment flow remains separate
whether manual fallback is sustainable

Burden levels:

LOW
\= staff can handle easily

MEDIUM
\= manageable but needs improvement

HIGH
\= POS integration or workflow change needed

CRITICAL
\= manual fallback blocks service value

Core rule:

Manual POS fallback is valid interim operation, but repeated high burden becomes POS integration signal.

13\. POS Integration Readiness Signal

First 30 days may reveal POS integration need.

POS readiness signals:

request volume is meaningful
manual POS entry burden is high
staff complains about duplicate entry
merchant asks for POS connection
menu/options must match POS
table/order handoff needs automation
medium or large store
multi-staff operation
preorder flow grows

Possible actions:

mark POS\_INTEGRATION\_INTEREST
check POS provider
check provider adapter availability
check menu mapping readiness
check table mapping need
explain integration roadmap
avoid unsupported promise

Core rule:

POS integration should be triggered by operational need and provider readiness.

KDS readiness signals:

kitchen misses request

group/preorder prep becomes important

remake/retry tracking needed
delay visibility needed
large or complex store

Possible actions:

mark KDS\_READINESS\_INTEREST
record kitchen pain point
record current kitchen workflow
check POS dependency
explain KDS roadmap carefully
avoid unsupported KDS promise

Core rule:

KDS readiness should be based on kitchen execution friction, not sales ambition.

19\. Conversion Readiness Criteria

Conversion readiness may be marked when:

activation passed
menu is stable
request board is understood
usage evidence exists
merchant sees value
staff burden is acceptable
support cases are resolved or acceptable
manual POS fallback is acceptable or POS roadmap is explained
pricing/plan is understood
trial expiry is understood
no major trust blocker remains

Core rule:

Conversion readiness means merchant can reasonably decide paid continuation.

20\. Conversion Blockers

Conversion blockers include:

menu not trusted
request board not used
manual POS burden too high
merchant unreachable
support issue unresolved
pricing not accepted
POS integration required but unavailable
KDS integration required but unavailable
trial value not proven
sales promise mismatch

Core rule:

Conversion blocker must be named explicitly, not hidden behind low enthusiasm.

21\. Conversion Readiness Outcome

Suggested outcomes:

READY\_FOR\_CONVERSION
READY\_WITH\_ADD\_ON\_DISCUSSION
READY\_WITH\_POS\_INTEGRATION\_INTEREST
READY\_WITH\_KDS\_INTEREST
NEEDS\_MORE\_SUPPORT
LOW\_USAGE\_REVIEW\_REQUIRED
CONVERSION\_BLOCKED
NOT\_A\_FIT

Meaning:

READY\_FOR\_CONVERSION
\= paid continuation can be discussed

READY\_WITH\_ADD\_ON\_DISCUSSION
\= base service works and add-ons may be discussed

READY\_WITH\_POS\_INTEGRATION\_INTEREST
\= paid conversion may depend on POS path

READY\_WITH\_KDS\_INTEREST
\= paid conversion may depend on kitchen path later

NEEDS\_MORE\_SUPPORT
\= more troubleshooting required

LOW\_USAGE\_REVIEW\_REQUIRED
\= evidence is insufficient

CONVERSION\_BLOCKED
\= major blocker exists

NOT\_A\_FIT
\= merchant is unlikely to benefit now

22\. Trial Extension Consideration

Trial extension may be considered when:

activation was delayed
merchant used service but support issue blocked value
menu correction took longer than expected
seasonal or temporary closure occurred
POS/KDS clarification is pending
HQ approves extension

Trial extension should not be automatic.

Core rule:

Trial extension requires reason, evidence, and approval.

30\. Relationship To First 7 Days Activation

First 30 Days review depends on First 7 Days Activation Check.

If activation failed:

first 30 days review should not mark conversion readiness

If activation partially passed:

carry unresolved activation issues into first 30 days troubleshooting

If activation passed:

focus on usage, habit, and value proof

Core rule:

Do not evaluate conversion readiness on top of unresolved activation failure.

31\. Relationship To AI Menu Stabilization

Menu issues discovered during first 30 days should create or update menu stabilization workflow.

Core rule:

Menu stabilization is a conversion prerequisite when menu trust affects operation.

32\. Relationship To Request Board Adoption

Request board adoption review should feed staff operation policy.

Core rule:

Request board usage must become store habit before request volume becomes meaningful.

33\. Relationship To POS Manual Fallback

Manual POS fallback review should feed POS integration readiness.

Core rule:

Manual fallback burden is the practical bridge between Stage 0 and POS integration.
