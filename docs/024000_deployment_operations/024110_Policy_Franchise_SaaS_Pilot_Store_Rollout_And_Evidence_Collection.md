# 024110_Policy_Franchise_SaaS_Pilot_Store_Rollout_And_Evidence_Collection

Legacy path: $old.

## 1. Purpose

This document defines the pilot store rollout, test-store evidence collection, SaaS validation, Franchise OS linkage readiness, provider gateway verification, and hardware partner preparation policy for the Yoonsul Wait/Order Handoff project.

The previous documents established:

- Toss as primary base provider direction
- OKPOS as required compatibility interface
- PAYCO as secondary payment / smart-order channel
- Provider Gateway as strategic leverage
- Mini Kiosk and KDS as future operational modules
- Store OS and Franchise OS as SaaS revenue layers
- HQ/store billing responsibility boundaries

This document defines how the project should collect operational evidence from the first store and nearby pilot stores before expanding into Franchise OS-linked SaaS.

This document does not launch pilot stores, sign vendor contracts, implement SaaS billing, or deploy production systems.

It defines rollout and evidence policy only.

## 3. Core Principle

Pilot rollout must prove operational value, not only technical connection.

The project must follow this rule:

> A provider connection, kiosk screen, or KDS ticket is not enough. The pilot must prove that Yoonsul improves store operation, reduces handoff friction, supports recovery, creates useful evidence, and can scale into Franchise OS.

Technical success without operational adoption is incomplete.

Operational adoption without evidence is not scalable.

---

## 4. Rollout Stages

Recommended rollout stages:

| Stage | Purpose |
| ----- | ------- |
| Stage 0 Documentation | Policy, provider research, architecture boundary |
| Stage 1 First Store Internal Test | Yoonsul-owned store runtime evidence |
| Stage 2 Nearby Friendly Store Test | controlled external store validation |
| Stage 3 Limited Pilot Cluster | 3 to 5 stores with controlled provider mix |
| Stage 4 SaaS Pilot Package | paid or semi-paid SaaS package test |
| Stage 5 Franchise OS Linkage Test | HQ/store governance connection |
| Stage 6 Hardware Partner Bundle Test | standardized device and support package |
| Stage 7 Phase 2 Provider Expansion | selected additional provider verification |
| Stage 8 Franchise-Ready Rollout | repeatable onboarding and billing |

The project should not skip directly from Stage 1 to franchise-scale rollout.

## 6. Stage 1 First Store Internal Test

The first Yoonsul-owned store should prove:

- POS/provider stack selection
- payment/order flow
- handoff reliability
- KDS or kitchen output path
- staff workflow
- customer order flow
- manual recovery
- provider failure handling
- menu/sold-out update
- refund/cancel process
- owner dashboard usefulness
- support burden
- hardware reliability
- daily operational discipline

The first store is both a business and a runtime laboratory.

## 7. First Store Evidence Categories

First store evidence should include:

| Evidence Category | Examples |
| ----------------- | -------- |
| Order Evidence | order count, source, duplicate prevention |
| Payment Evidence | approval, failure, refund, uncertainty |
| Handoff Evidence | POS/KDS transition, delay, retry |
| KDS Evidence | ticket created, accepted, completed, delayed |
| Staff Evidence | staff usage, mistake, training need |
| Customer Evidence | customer flow, wait time, confusion, cancellation |
| Provider Evidence | Toss/OKPOS/PAYCO event behavior |
| Recovery Evidence | timeout, duplicate tap, manual correction |
| Support Evidence | issue type, time to resolve, owner |
| Hardware Evidence | device failure, printer issue, network issue |
| Dashboard Evidence | owner/HQ visibility value |
| SaaS Value Evidence | what feature store would pay for |

Evidence should be structured from the beginning.

## 8. Stage 2 Nearby Friendly Store Test

Nearby friendly store tests should be used after internal first-store proof.

Purpose:

- test outside Yoonsul-owned environment
- test installation friction
- test vendor/dealer support
- test store owner understanding
- test staff adoption without founder presence
- test SaaS value perception
- test provider variability
- test support workload
- test pricing sensitivity
- test data access limitation

Friendly store test must be controlled.

Do not overpromise full franchise capability.

---

## 9. Friendly Store Selection Criteria

Select friendly pilot stores that:

- are nearby enough for support
- have owner willing to test
- have manageable order volume
- use relevant POS/payment stack
- allow evidence collection
- accept limited pilot scope
- can provide operational feedback
- do not require complex custom features
- can tolerate controlled experimentation
- have clear support contact

Avoid pilot stores that:

- demand full custom integration
- require many unsupported POS providers
- have hostile staff environment
- have unclear ownership
- cannot share evidence
- need immediate production-grade SLA
- rely on complex legacy setup

---

## 10. Pilot Scope Agreement

Every pilot should define:

- pilot duration
- included modules
- excluded modules
- provider stack
- device scope
- support scope
- fee or free pilot status
- data collection permission
- evidence use permission
- staff training responsibility
- rollback path
- incident escalation
- end-of-pilot review
- conversion decision

Pilot scope must be written.

Verbal pilot understanding is not enough.

---

## 11. Stage 3 Limited Pilot Cluster

After one or two friendly store tests, create a limited pilot cluster.

Recommended size:

    3 to 5 stores

Purpose:

- test repeatability
- compare provider stacks
- observe support burden
- validate onboarding checklist
- validate billing assumptions
- validate hardware profiles
- validate staff training
- validate owner dashboard
- validate Franchise OS data shape

Do not exceed 5 stores before support process is stable.

---

## 12. Pilot Provider Mix

Pilot provider mix should be controlled.

Recommended mix:

- Toss-first store
- OKPOS-installed store
- optional PAYCO payment test store
- one store with small kiosk vendor only if transparency is adequate
- no Phase 2 provider unless specifically authorized

Do not add Smartro/KICC/NICE/Hyphen to early pilot cluster unless Phase 2 is active.

---

## 13. SaaS Value Validation

Pilot must answer:

- would the store pay monthly for this?
- which module creates the most value?
- does KDS visibility matter?
- does Mini Kiosk reduce staff burden?
- does payment recovery reduce disputes?
- does owner dashboard change decisions?
- does support/evidence reduce anxiety?
- does Provider Gateway matter to the store?
- does store understand the package?
- does store prefer one bundled price or modular add-ons?

SaaS pricing should follow evidence.

---

## 14. Provider Gateway Validation

Provider Gateway validation should measure:

- provider data access
- merchant/store mapping correctness

- duplicate prevention
- provider failure handling
- payment/order reconciliation
- local daemon recovery
- webhook/callback reliability
- support debugging
- adapter disable/rollback

Provider Gateway value is proven when provider differences become manageable.

## 24. Pilot Success Criteria

Pilot is successful when:

- core order/payment/handoff flow is stable
- recovery cases are visible and resolved
- staff can operate without founder intervention
- owner sees clear value
- provider issues are diagnosable
- KDS or kitchen flow improves
- Mini Kiosk improves order flow or reduces burden
- evidence packets are complete
- support burden is measurable
- pricing hypothesis becomes clearer
- next store onboarding is easier

Pilot is not successful just because software ran.

---

## 25. Pilot Failure Criteria

Pilot should be considered failed or paused when:

- payment truth is unclear
- duplicate orders occur repeatedly
- KDS/kitchen output is unreliable
- staff bypass the system
- owner sees no value
- support burden is too high
- vendor/dealer ownership is unclear
- data access is insufficient
- recovery state is hidden
- hardware failures dominate
- pilot scope keeps expanding without control

Failed pilot is still useful if evidence is captured.

---

## 26. Franchise OS Linkage Readiness

Franchise OS linkage should begin only when pilot evidence proves:

- store data is reliable
- order/payment/KDS states are understandable
- owner dashboard has value
- support/recovery process works
- provider gateway can handle real variability
- staff adoption is adequate
- module pricing is plausible
- onboarding can be repeated
- evidence can be standardized
- HQ-level governance data can be derived

Franchise OS should not be linked to unstable store runtime.

---

## 27. SaaS Readiness Gate

SaaS package should be considered ready for external sale only when:

1. package scope is clear
2. pricing hypothesis is supported by evidence
3. support burden is known
4. provider stack is stable enough
5. onboarding checklist exists
6. rollback path exists
7. data access is adequate
8. billing responsibility is clear
9. evidence packet is complete
10. customer/store value is visible

Do not sell full SaaS before these gates are met.

---

## 28. Hardware Partner Readiness Gate

Hardware partner program should begin only when:

- device requirements are known
- failure patterns are known
- support model is known
- Mini Kiosk/KDS hardware needs are known
- payment terminal requirements are known
- installation process is repeatable
- replacement process is known
- software runtime is not hardware-locked
- pilot stores confirm hardware value

Hardware partner should follow pilot evidence.

## 31. Anti-Patterns

The following are prohibited:

- treating first store success as franchise readiness
- scaling before evidence is structured
- adding too many providers during pilot
- using pilot store as custom development dump
- promising full SaaS during test
- ignoring support burden
- ignoring staff adoption
- ignoring hardware failures
- ignoring payment uncertainty
- hiding failed pilot evidence
- treating friendly store feedback as market proof
- starting hardware partnership before software needs are clear
- linking Franchise OS before store runtime is stable

## 34. Conclusion

Yoonsul should move from documentation to first-store proof, then nearby pilot evidence, then limited pilot cluster, then SaaS package validation, and only later Franchise OS linkage.

The correct path is:

- document boundaries first
- test in first Yoonsul store
- collect structured evidence
- test nearby friendly stores
- keep pilot scope controlled
- prove Toss base
- prove OKPOS compatibility
- measure Mini Kiosk and KDS value
- measure payment recovery value
- measure support burden
- validate SaaS pricing hypothesis
- link Franchise OS only after store runtime is stable
- pursue hardware partners only after device needs are proven

This document prevents premature scaling and prepares the project for evidence-based SaaS and Franchise OS expansion.
