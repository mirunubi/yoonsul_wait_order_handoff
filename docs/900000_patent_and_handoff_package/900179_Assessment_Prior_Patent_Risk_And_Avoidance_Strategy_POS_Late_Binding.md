## 0. Document Purpose

이 Assessment 문서는 구두주문 후행 바인딩 결제 시스템(900162)의
선행특허 리스크를 분석하고 회피 전략을 정의한다.

```text
판단 기준:
  변리사 검토 후 특허 가능 → 900162 유지
  특허 불가 판정 → 900162 + 900163 파기

이 문서는 실패 가능성을 전제로 작성된다.
```

---

## 1. 선행특허 위험도 분석

### 1.1 KR102160469B1 — 위험도: 최고

```text
명칭: 거래 중개 서버 및 거래 정보 등록 방법

핵심 청구:
  구두주문 → POS 입력
  → 서버에 가맹점 식별 정보와 거래 정보 매칭 등록
  → 단일 QR 코드 스캔
  → 고객 단말 조회 요청
  → 서버가 거래 정보 가공 송출
  → 모바일 결제 실행

우리 구조와 겹치는 부분:
  구두주문 → POS 입력                    ← 동일
  서버에 주문 등록 (unbound_order)        ← 동일
  단일 QR 스캔 → 주문 조회               ← 동일
  후행 바인딩 → 결제                     ← 동일

판정:
  우리 핵심 흐름 전체가 이 특허 범위 안에 있음
  신규성 거절 리스크 직접적
  가장 위험한 선행특허
```

---

### 1.2 US20140222545A1 — 위험도: 높음

```text
명칭: OPOS 드라이버 수준 데이터 분석 및 동적 영수증 생성

핵심 청구:
  OPOS 표준 드라이버 레이어 후킹
  → 주방/영수증 프린터 출력 데이터 파싱
  → 모바일 웹 매핑 동적 QR 코드 주입
  → 고객 결제 연결

우리 구조와 겹치는 부분:
  900162 Route C (주방프린터 출력 데이터 복제) ← 직접 충돌

판정:
  Route C 는 특허 클레임 불가
  구현은 가능하나 특허 보호 범위 외
  Route A (공식 API), Route B (로컬 DB),
  Route D (KDS 연동) 만 특허 대상으로 유지
```

---

### 1.3 CN104106276A / WO2013056104A1 — 위험도: 중간

```text
명칭: POS 프로토콜 추상화 방법

핵심 청구:
  ESC/POS, OPOS, JavaPOS 등
  다양한 POS 프로토콜을 추상화 엔진으로 변환
  → 모바일 지갑과 통신

우리 구조와 겹치는 부분:
  POS Gateway 표준 이벤트 변환 계층 ← 유사

판정:
  POS 프로토콜 추상화 자체는 특허 불가
  단, 우리 표준 이벤트 모델의
  "운영 이벤트 연동" 부분은 별개 영역
  추상화 계층은 구현하되 특허 클레임 제외
```

---

### 1.4 US8632000B2 (Paydiant) — 위험도: 높음

```text
명칭: 간편 결제 및 테이블 결제 기술

핵심 청구:
  모바일 기기 세션을 특정 거래 내역과 토큰 매칭
  POS 하드웨어 없이 클라우드 결제 완결
  pay-at-table 처리

우리 구조와 겹치는 부분:
  모바일 세션 + 거래 토큰 바인딩 ← 직접 충돌
  테이블 결제 클라우드 완결       ← 직접 충돌

판정:
  바인딩 + 테이블 결제 조합 자체는 이미 선점
  단, KDS 연동 없음이 우리 차별점
```

## 2. 막힌 영역 정리

```text
특허 클레임 불가 (선행특허 선점):

  구두주문 → QR 스캔 → 주문 조회 → 결제
  (KR102160469B1)

  주방프린터 파싱 → QR → 결제
  (US20140222545A1)

  (CN104106276A / WO2013056104A1)

  모바일 토큰 + 테이블 결제 클라우드 완결
  (US8632000B2)
```

## 3. 선행특허들의 공통 한계 (회피 포인트)

```text
선행특허 4개 모두 결제 완료로 끝난다.

결제 후 무슨 일이 일어나는지 없다:
  KDS 와 연결 없음
  대기열 세션과 연결 없음
  운영 이벤트 (품절/지연/장애) 연동 없음
  주문 변경 중간 검증 없음 (버전/fingerprint)
  결제 전 조리 차단 개념 없음

이 부분이 우리의 회피 영역이다.
```

---

## 4. 회피 전략 — 특허 클레임 재정의

### 4.1 기존 클레임 (위험)

```text
구두주문 → QR → 후행 바인딩 → 결제
→ KR102160469B1 과 정면 충돌
→ 특허 불가
```

### 4.2 수정 클레임 (회피 방향)

```text
핵심 이동:
  "결제까지"가 아니라
  "결제 후 KDS 연동"이 우리 특허의 시작점

수정 클레임:

  결제 승인 완료 이벤트를 트리거로
  주방 디스플레이(KDS)의 주문 티켓을
  HOLD → COMMITTED 로 자동 전환하고,

  대기열 세션 상태, 실시간 재고/품절 이벤트,
  주문 버전 검증을 결제 실행 조건으로
  통합 관리하여,

  결제 전 조리 차단 /
  결제 후 조리 허용을 보장하는
  운영 안전형 결제-KDS 연동 시스템
```

## 5. 회피 후 특허 가능 영역

```text
Patent 2 (기존, 이미 정의):
  KDS Late Binding
  HOLD → COMMITTED (결제 후만)
  → 이 자체는 선행특허에 없음
  → 가장 강한 특허

Patent A 보완:
  운영 이벤트 → KDS 상태 자동 전환
  (품절 → KDS 차단, 결제 → KDS 활성화)
  → 선행특허와 다른 영역

추가 회피 포인트:

  1. 주문 버전/fingerprint 검증
     결제 직전 주문 변경 감지 → 자동 차단
     선행특허에 이 개념 없음

  2. 대기 세션 + 사전 주문 + 결제 + KDS 연속 파이프라인
     대기 중 사전 주문 생성
     → 대기 상태에서 KDS HOLD 유지
     → 착석 후 결제
     → KDS COMMITTED 전환
     이 전체 파이프라인은 선행특허에 없음

  3. POS 연동 수준별 KDS 연동 모드 전환
     Level 0~3 에 따라
     KDS 전환 방식도 자동 변경
     선행특허에 없음
```

## 6. 변리사 검토 요청 사항

```text
검토 요청 1:
  KR102160469B1 의 청구항 범위가
  우리 구조 전체를 포함하는지 확인
  → 특히 "단일 QR 스캔 + 서버 매칭" 부분

검토 요청 2:
  KDS Late Binding (Patent 2) 이
  위 4개 선행특허를 회피하면서
  독립 특허로 성립 가능한지 확인

검토 요청 3:
  "결제 승인 → KDS HOLD → COMMITTED 자동 전환"
  이 조합이 신규성/진보성 인정 가능한지 확인

검토 요청 4:
  "대기 세션 + 사전 주문 + 착석 후 결제 + KDS 활성화"
  전체 파이프라인의 특허 가능성

검토 요청 5:
  주문 버전/fingerprint 기반
  결제 전 주문 변경 차단 기술의
  선행특허 존재 여부 확인
```

## 7. 시나리오별 대응

```text
시나리오 A: Patent 2 단독 특허 가능
  KDS Late Binding 만으로 특허 출원
  구두주문 바인딩은 구현만, 특허 제외

시나리오 B: 대기 파이프라인 특허 가능
  대기 세션 + 사전 주문 + 결제 + KDS 연속 흐름
  이것이 Patent 1 + Patent 2 결합 특허

시나리오 C: 모두 불가
  900162 + 900163 파기
  구현은 유지, 특허 포기
  경쟁 우위는 속도와 운영 완성도로 확보

시나리오 D: 부분 가능
  회피 설계로 청구항 범위 축소 후 출원
  KDS 연동 부분만 클레임
```

## 8. 파기 조건

```text
아래 중 하나라도 해당하면 900162 + 900163 파기:

  [ ] KR102160469B1 이 우리 전체 흐름을 포함
      AND Patent 2 (KDS Late Binding) 도 종속항으로 포함
  [ ] 변리사가 신규성 없음 판정
  [ ] 선행특허 5개 이상 추가 발견으로 회피 불가

파기 시:
  900162 삭제
  900163 삭제
  900160/900161 에서 POS 후행 바인딩 관련 섹션 제거
  Patent 2 (KDS Late Binding) 는 유지

파기 후 전략:
  특허 포기 + 구현 속도로 시장 선점
  오픈 소스화로 진입 장벽 역이용
```
