## 0. Document Purpose

이 Policy 문서는 여신전문금융업법(여전법) 규제 대응 원칙과
캐치메뉴 테이블오더 결제 구조 설계 기준을 정의한다.

핵심 원칙:

```text
캐치메뉴는 결제 단말기가 아니다.
캐치메뉴는 PG 연동사다.
카드 정보는 캐치메뉴 서버를 통과하지 않는다.
실물 카드 결제는 인증된 POS 단말기에서만 처리한다.
테이블 결제는 간편결제(앱카드/간편결제) 전용이다.
```

## 1. 여전법 규제 핵심 요약

```text
근거법:
  여신전문금융업법 제27조의4
  동법 시행령 제7조의6
  금융위원회 / 여신금융협회 신용카드 단말기 정보보호 기술기준

규제 내용:
  카드 신용정보를 처리하는 모든 단말기는
  여신금융협회 인증 + 의무 등록 필요

하드웨어 요건:
  메모리 자동 파괴 기술
  물리적 분해 방지 메커니즘
  종단간(E2E) 암호화 칩 탑재

SW POS 추가 요건:
  키인(Key In) 거래 시 랜덤 배열 키패드 강제
  일반 OS 키보드 사용 원천 금지
  결제 완료 즉시 메모리에서 카드정보 영구 삭제
  취약점 점검 수검 의무

현실:
  기술력 약한 소형 개발사는 독자 SW POS 출시 불가
  인증된 IC카드 리더기 동글 부착 방식으로 우회
```

## 2. 캐치메뉴 포지션 확정

```text
캐치메뉴 = PG 연동사 (Payment Gateway 사용자)
캐치메뉴 ≠ 결제 단말기 운영자
캐치메뉴 ≠ 카드 정보 처리자

결제 처리 주체:
  토스페이먼츠 (여신협회 인증 보유)
  OKpos / 토스POS (인증된 실물 단말기)

캐치메뉴 역할:
  토스페이먼츠 SDK 호출
  결제 결과(승인번호, 금액, 시각) 수신
  카드 정보 = 캐치메뉴 서버 미통과
  payment_ledger 에 결제 결과만 저장

이 구조면 여전법 적용 대상 아님
```

## 3. 결제 수단별 테이블 허용 기준

| 결제 수단 | 테이블 허용 | 처리 방법 | 근거 |
|---|---|---|---|
| 카카오페이 | ✓ | 토스페이먼츠 SDK | 간편결제 |
| 네이버페이 | ✓ | 토스페이먼츠 SDK | 간편결제 |
| 토스페이 | ✓ | 토스페이먼츠 SDK | 간편결제 |
| 삼성페이 | ✓ | 토스페이먼츠 SDK | 간편결제 |
| 앱카드 (삼성/현대/신한 등) | ✓ | 토스페이먼츠 SDK | 앱카드 |
| 실물 신용카드 IC | ✗ | 계산대 POS 단말기만 | 여전법 |
| 실물 체크카드 | ✗ | 계산대 POS 단말기만 | 여전법 |
| 실물 카드 마그네틱 | ✗ | 계산대 POS 단말기만 | 여전법 |
| 현금 | ✗ | 계산대에서 처리 | 운영 정책 |
| 현금영수증 | ✗ | 계산대 또는 고객 직접 | 국세청 규정 |

## 4. 테이블오더 결제 설계 원칙

### 4.1 허용 설계

```text
고객이 테이블에서 결제:
  고객 스마트폰 앱 또는 웹앱
  → 토스페이먼츠 결제창 호출
  → 간편결제 선택 (카카오/네이버/토스/앱카드)
  → 토스페이먼츠 서버에서 처리
  → 승인 결과 → 캐치메뉴 서버 수신
  → payment_ledger APPROVED 기록
  → KDS COMMITTED 전환 (Patent 2)

카드 정보 흐름:
  고객 스마트폰 → 토스페이먼츠 서버
  캐치메뉴 서버는 결과만 수신
  카드번호/유효기간 = 캐치메뉴 미보유
```

### 4.2 금지 설계

```text
금지 1: 실물 카드 정보 직접 입력
  테이블 태블릿에 카드번호 입력란 없음
  Flutter 화면에 카드번호 입력 필드 없음

금지 2: 범용 키보드로 카드 정보 수집
  여전법: 랜덤 배열 키패드 강제
  구현 복잡도 + 인증 부담 → 전면 회피

금지 3: 캐치메뉴 서버에 카드 정보 저장
  payment_ledger 저장 항목:
    pg_transaction_id (토스 승인번호)
    approved_amount
    approved_at
    payment_method_type (간편결제 종류)
  저장 금지:
    card_number
    card_expiry
    cvv
    주민번호
```

### 4.3 고객 화면 설계 원칙

```text
테이블 결제 화면:
  "결제하기" 버튼 클릭
  → 간편결제 목록 표시
     카카오페이 / 네이버페이 / 토스 / 앱카드
  → 선택 → 토스페이먼츠 결제창 이동
  → 완료 → 결과 화면

실물 카드 안내:
  "실물 카드 결제는 계산대를 이용해 주세요"
  버튼 또는 안내 문구로 명시

현금 안내:
  "현금 결제는 직원에게 말씀해 주세요"
```

## 5. POS 단말기 연동 원칙

```text
실물 카드 결제 흐름:
  고객이 계산대로 이동
  또는 직원이 이동식 단말기 가져옴
  → OKpos / 토스POS 단말기에서 카드 처리
  → 여신협회 인증 단말기가 카드 정보 처리
  → 결제 완료 이벤트 → 캐치메뉴 수신
  → payment_ledger APPROVED 기록

캐치메뉴 역할:
  POS 결제 완료 이벤트 수신만
  카드 정보 처리 없음
```

## 6. 현금영수증 처리

```text
국세청 규정:
  현금영수증 발행 의무 (건당 10만원 이상)
  가맹점은 현금영수증 발행 장치 보유 의무

캐치메뉴 대응:
  현금 결제 = POS 에서 처리 (캐치메뉴 외부)
  현금영수증 = OKpos/토스POS 에서 발행
  캐치메뉴는 현금 결제 처리 안 함

향후 Edge Function (Phase 3):
  cash_receipt_request()
  국세청 현금영수증 API 연동 가능
  단, 현금 결제 자체는 POS 에서
```

## 7. Flutter 구현 체크리스트

```text
결제 화면 필수 확인:
  [ ] 카드번호 입력 필드 없음
  [ ] 유효기간 입력 필드 없음
  [ ] CVV 입력 필드 없음
  [ ] 일반 키보드 카드 입력 없음

간편결제 표시:
  [ ] 토스페이먼츠 SDK 사용
  [ ] 카카오페이 / 네이버페이 / 토스 / 앱카드 표시
  [ ] 실물 카드 = 계산대 안내 문구 표시

저장 금지 확인:
  [ ] payment_ledger 에 카드번호 저장 없음
  [ ] Flutter SharedPreferences 에 카드 정보 없음
  [ ] SecureStorage 에 카드 정보 없음
  [ ] 로그에 카드 정보 없음
```

## 8. 법적 리스크 요약

```text
낮은 리스크 (우리 구조):
  토스페이먼츠 SDK 통한 간편결제
  카드 정보 미처리
  PG 연동사 포지션

중간 리스크 (주의 필요):
  테이블 태블릿에 실물 카드 리더기 부착 시
  → 여신협회 인증 단말기만 사용
  → 자체 제작 리더기 금지

높은 리스크 (절대 금지):
  범용 태블릿 소프트웨어로 카드번호 직접 처리
  카드 정보 캐치메뉴 서버 저장
  미인증 SW POS 단독 카드 결제 처리
```
