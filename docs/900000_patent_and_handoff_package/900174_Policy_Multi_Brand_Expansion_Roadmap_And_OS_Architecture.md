## 0. Document Purpose

이 Policy 문서는 윤슬 멀티브랜드의 단계별 확장 로드맵과
각 브랜드가 윤슬OS + 캐치메뉴 위에 올라타는
공통 아키텍처를 정의한다.

```text
핵심 원칙:
  브랜드가 달라도 OS 는 하나
  각 브랜드 = tenant_id 로 격리
  공통 파이프라인 = 재사용
  브랜드 특화 = 설정으로 처리
```

---

## 1. 공통 OS 아키텍처

```text
[윤슬OS + 캐치메뉴 공통 레이어]

  인프라:
    Supabase (PostgreSQL + Realtime)
    Flutter (Android/iOS/Web/Windows)
    토스페이먼츠 (결제)
    FCM (푸시 알림)

  공통 파이프라인:
    대기 → 사전 주문 → 착석
    → 결제 → KDS COMMITTED
    → 서빙 → 완료 → 감사 로그

  브랜드 격리:
    tenant_id = 브랜드별 고유 UUID
    brand_id  = 브랜드 식별자
    RLS 로 데이터 완전 격리

[브랜드 레이어]
  브랜드 설정:
    메뉴 구성 (SKU)
    알레르겐 설정
    영업시간
    KDS 조리 시간 기준
    쿠폰 정책
    브랜딩 (로고/색상/앱 이름)

  브랜드 특화 AI:
    메뉴 임베딩 (벡터)
    수요 예측 모델
    SOP 자가진화
```

## 2. 브랜드별 상세 설계

### Brand 1: 윤슬김밥

```text
브랜드 특성:
  김밥 전문 (64개 메뉴)
  빠른 회전율 (5~7분 조리)
  도시락 포장 비중 높음
  외국인 방문객 대응 중요

OS 특화 설정:
  KDS: 조리 시간 5~7분 기준
  DID: 대기 번호 + 김밥 조리 현황
  키오스크: 알레르겐 필터 강조
  다국어: ko/en/zh/ja/vi/th

AI 활용:
  피크타임 인기 메뉴 예측
  알레르겐 자동 안내
  외국인 메뉴 추천 (벡터 검색)

쿠폰 전략:
  스탬프 10회 → 기본김밥 무료
  재방문 7일 내 → 음료 무료
  단체 4인 이상 → 10% 할인

Phase 1 목표:
  서울 1호점 일평균 주문 50+
  대기 → 착석 전환율 80%+
  KDS 지연율 5% 미만
```

### Brand 2: 윤슬보울

```text
브랜드 특성:
  보울 전문 (한식/아시안 베이스)
  커스터마이징 중심
  건강식 포지셔닝
  점심 수요 집중

OS 특화 설정:
  KDS: 재료별 준비 + 조합 단계
       조리 시간 7~10분
  키오스크: 재료 선택 UI 중심
            영양 정보 실시간 표시
  DID: 보울 준비 현황

AI 활용:
  재료 조합 추천 (벡터 유사도)
  영양 정보 자동 계산
  점심 수요 예측
  인기 조합 실시간 업데이트

쿠폰 전략:
  첫 방문 → 재료 업그레이드 무료
  월 5회 이상 → VIP 가격
  특정 재료 조합 → 할인

메뉴 SKU 전략:
  기본 보울 5종
  재료 선택 20종
  소스 선택 10종
  조합 무한대 → 단순 운영
```

### Brand 3: 야식 브랜드

```text
브랜드 특성:
  야간 특화 (오후 9시~새벽 2시)
  배달 중심 (홀 최소화)
  술자리 안주류
  빠른 배달이 핵심

OS 특화 설정:
  영업시간: 21:00~02:00
  KDS: 배달 우선순위 자동 정렬
  배달앱: 배민/요기요/쿠팡 슬롯 최우선
  슬롯 컨테이너: 배달앱 Agent 강화

AI 활용:
  야간 수요 예측 (요일/날씨/이벤트)
  배달 최적 시간 분석
  심야 재고 자동 발주
  배달앱 주문 우선순위 AI 분류

쿠폰 전략:
  첫 주문 → 무료 안주 추가
  자정 이후 → 야간 특가
  단골 → 배달비 무료

운영 특화:
  재고 소진 이벤트 → 즉시 DID/앱 안내
  심야 직원 최소화 → AI 자동화 극대화
  배달 지연 → 고객 자동 안내
```

### Brand 4: 음료 브랜드

```text
브랜드 특성:
  음료 전문
  빠른 회전율 (1~3분)
  키오스크 중심 운영
  테이크아웃 90%+

OS 특화 설정:
  KDS: 음료 제조 시간 1~3분
       동시 제조 최적화
  키오스크: 음료 주문 UI 최적화
            얼음/온도/사이즈 빠른 선택
  DID: 음료 준비 번호 대형 표시
  대기: 최소화 (즉석 제조)

AI 활용:
  날씨/계절 수요 예측
  인기 조합 자동 추천
  제조 시간 KDS 최적화
  원가율 실시간 알림

쿠폰 전략:
  10잔 스탬프 → 1잔 무료
  날씨 더움 → 아이스 할인
  특정 시간대 → 1+1

운영 특화:
  직원 최소화 (키오스크 + KDS)
  피크타임 제조 병목 AI 예측
  재료 원가율 실시간 관리
```

## 3. 공통 운영 파이프라인 재사용

```text
4개 브랜드 모두 동일:

  대기 등록 → wait_number 발급
  사전 주문 → KDS HOLD 생성
  착석 처리 → table_id 바인딩
  결제 확인 → KDS COMMITTED
  조리 시작 → COOKING
  완료 → SERVED
  감사 로그 → ledger.events

브랜드별 다른 것:
  menu_items (메뉴 구성)
  estimated_minutes (조리 시간 기준)
  kitchen_zone (조리 구역 구성)
  coupon_policy (쿠폰 정책)
  branding (로고/색상)
  operating_hours (영업시간)

이것이 OS 위에 브랜드가 올라타는 구조
```

## 5. 멀티브랜드 운영 원칙

```text
원칙 1: 단일 OS
  모든 브랜드 = 하나의 윤슬OS
  브랜드별 설정만 다름

원칙 2: 데이터 격리
  tenant_id + brand_id 완전 격리
  브랜드 간 고객 데이터 비공유
  (캠페인 동의 시 교차 마케팅만)

원칙 3: AI 공유
  각 브랜드 데이터 → 공통 AI 학습
  크로스 브랜드 인사이트 생성
  단, 개별 브랜드 데이터는 격리

원칙 4: 점진적 확장
  한 브랜드씩 검증 후 확장
  실패해도 OS 에 영향 없음
  브랜드만 드롭하면 됨

원칙 5: 표준화 우선
  운영 표준화 후 AI 적용
  표준 없이 AI 먼저 적용 금지
  SOP → AI 순서 준수
```
